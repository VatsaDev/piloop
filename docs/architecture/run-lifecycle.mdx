title: One run's life
description: What the daemon does between a ready idea and the verdict on each of its commits.
---

A **run** is one attempt at an idea. The scheduler queues it on a tick. A thread of the daemon then executes it:
the agent, the scores and the verdicts. The agent and each evaluation are jobs of the
[executor](/architecture/extension-points#executors). This page shows the built-in `workers`, whose worker takes each
job on a [lease](/architecture/leases).

## The steps

1. **Queue.** On each tick, the scheduler fills the free implementer slots with runnable ideas. An idea is runnable when
   it is `ready` and each of its prerequisites (an `after` link) is `done`. The slot goes to the most urgent idea of
   the track that is furthest below its share. At least one run in `[roles.implementer] explore_every` starts from a
   pinned idea when one is ready. The scheduler inserts a `queued` run, chooses its harness from the rotation, and
   inserts a `requested` agent session row. A [role that does runs](/concepts/roles#define-a-role-that-does-runs) fills its
   own slots in the same way, with the ideas that its `takes` condition selects, before the implementer.
2. **Take.** In the same tick, the scheduler sets `requested` rows to `starting`, up to `max_concurrent` for each role
   and each harness. Each one goes to a thread of the daemon's pool.
3. **Launch.** The run controller writes the brief. The launcher fills in the harness's argv and submits the agent's
   job. The worker takes it, adds a git worktree at the run's base (the head, or the candidate that the idea
   pins) and calls `Runtime.start`.
4. **Work.** The agent reads its brief, implements the idea and commits. It reads and writes the database with
   `piloop sql`. On each tick, the scheduler hands new comments on the run or the idea to the executor, which sends
   them to the agent.
5. **Close.** When the agent ends, times out, or a minute after its finding, when the daemon ends it, the worker reads
   its token usage, commits what is left uncommitted, on its own, as a `recovered` commit, and reports, which closes
   the agent session row. The run controller closes the run. The implementer slot is now free for the next run.
6. **Score.** Each new commit becomes a candidate. Commits with the same git tree are the same candidate. The worker
   runs the evaluate command in a clean worktree of the commit, its report stores a measurement, and the daemon judges the candidate against the run's bar. A keep becomes the bar for the run's next commit. A `recovered` commit is not measured; if the run
   did not succeed, the idea goes back to the queue with it as its base, so a new implementer finishes it.
7. **Rebase.** When a keep's bar is no longer the head, because another run kept meanwhile, the keep is marked
   `interesting`. The daemon merges it onto the head, measures the merge and judges it there. A merge that conflicts
   files a seed.
8. **Settle.** The idea becomes `done`, or goes back to `ready` when its run failed and it has attempts left. The
   idea stays `scheduled` until every commit is judged, so an idea that waits for it starts from its keeps.

An agent that does not start to work is not an attempt. The run controller queues the run again with a new agent
session row, up to two times, then parks the idea. [State machines](/architecture/state-machines#run) says which ends
of a run are attempts, and [the verdict](/concepts/verdict) explains the bar and the head.

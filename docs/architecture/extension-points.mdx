configuration in `piloop.toml`, or with a Python package and an entry point. The tables come from the code.

|---|---|---|
| [Roles](#roles) | `[roles.<name>]` | `piloop.roles` |
| [Triggers](#triggers) | a `sql` trigger | `piloop.triggers` |
| [Runtimes](#runtimes) | no | `piloop.runtimes` |
| [Storage backends](#storage-backends) | no | `piloop.stores` |
| [Harnesses](#harnesses) | `[harness.<name>]` | no |

A package entry point goes in the package's `pyproject.toml`. Install the package in the environment of `piloop`.
piloop loads each group once per process. A name that a built-in has already is an error that names the entry point.

## Roles

### The contract

A role is a table in `piloop.toml`: what the agent is told (its prompt), when it starts (the run queue, or its
triggers), where it works (its runtime and working copy), how it works (harnesses, models, MCP servers, timeout,
concurrency) and what it may file. A role either does runs or sweeps. A role that does runs (`runs = true`) takes ideas
from the run queue, works in a new worktree at the base of its run, and its commits are scored and judged. A sweeping
role starts on its triggers, works at the head or in the project checkout, and nothing it commits is scored.
[Roles](/concepts/roles) describes each key.

### Built in

The built-in roles are the same tables with defaults, so a project can change any key of them:

|---|---|---|---|---|

| `research` | no | `low_water`, `seed` | `ideas` | Research develops seeds and keeps ideas ready for the workers. |

### Define a role

Add a table with a new name, a prompt file and at least one trigger. This role reads each new escalation in the inbox
and writes a plan for it, one agent at a time, in the project checkout:

```toml
[roles.planner]
prompt = "briefs/planner.md"
triggers = [
  { kind = "sql", when = "SELECT id FROM comments WHERE kind = 'escalation' AND acked_at IS NULL AND created_at > :since" },
]
workdir = "project"
max_concurrent = 1
timeout = 1200
files = "seeds"
writes = ["comments(finding) on the escalation", "seeds via idea seed"]
```

Then write the prompt and store the config:

```bash
mkdir -p briefs
printf '# Planner\nFor each new escalation, write a finding with a plan of three steps.\n' > briefs/planner.md
piloop init .
```

The daemon now checks the query on each tick. When it returns a row, the daemon requests a `planner` agent, and
`piloop status` lists it as `planner#<worker id>`. The agent signs its comments `planner#<worker id>`.

### Define a role that does runs

Add a table with a new name and `runs = true`. The role takes the worker's defaults, so every other key is optional.
This role runs the ideas of the `speed` track with Claude, two at a time, and stops each agent after 10 minutes:

```toml
model = { pi = "anthropic/claude-opus-5-5", claude = "claude-opus-5-5" }

[roles.sprinter]
runs = true
takes = "track = 'speed'"
prompt = "briefs/sprinter.md"
harnesses = ["claude"]
max_concurrent = 2
timeout = 600

[roles.worker]
takes = "track != 'speed'"
```

`takes` is an SQL condition on the `ideas` table, so it can select by any column: `priority`, `track`, `family`,
`harness`, or a subquery. Without `takes` on the worker, the worker also runs the `speed` ideas that wait for a free
`sprinter` slot. Write the prompt and store the config:

```bash
mkdir -p briefs
printf '# Sprinter\nMake the change that the idea names, measure it once, and commit.\n' > briefs/sprinter.md
piloop init .
```

The daemon queues each `speed` idea for a `sprinter` run. The run's agent signs `sprinter#<worker id>`, its brief has
the idea and the starting point as a worker's has, and its commits are scored and judged like a worker's.
[Roles](/concepts/roles#define-a-role-that-does-runs) lists which rules apply to each role and which apply to every run.

### Define your own in a package

A Python package adds roles and triggers through two entry point groups:

- `piloop.triggers`: each entry point names a subclass of `piloop.triggers.Trigger`. Its name is the `kind`. Its
  fields are its parameters. Its `fire(tick)` method returns a `Fire` (the reason, and how many agents) or None. `tick`
  gives it the session, the project, the role and the queries that the built-in triggers use (`piloop.triggers.Tick`).
- `piloop.roles`: each entry point names a `piloop.config.SweepRole` or a `piloop.config.WorkerRole` (a role that does
  runs), the defaults of the role. Its name is the name of the role. `piloop init` stores the role in the project's
  config, with the project's `[roles.<name>]` table over the defaults.

piloop loads each group once per process. A name that a built-in trigger or role has already is an error.

```python
from datetime import timedelta
from pathlib import Path
from typing import Literal

from sqlalchemy import func, select

from piloop.config import SweepRole
from piloop.db.models import Candidate, Verdict, utcnow
from piloop.triggers import Fire, Tick, Trigger


class NoKeep(Trigger):
    """``no_keep``: no new keep for ``hours`` hours, once per agent of the role."""

    kind: Literal['no_keep'] = 'no_keep'
    hours: float = 6

    def fire(self, tick: Tick) -> Fire | None:
        keeps = select(func.max(Candidate.created_at)).where(
            Candidate.project_id == tick.project.id, Candidate.verdict == Verdict.KEEP
        )
        latest = tick.s.scalar(keeps) or tick.project.created_at
        started = tick.last.started_at if tick.last is not None else latest
        if utcnow() - max(latest, started) < timedelta(hours=self.hours):
            return None
        return Fire(f'no keep for {self.hours:g} hours')


AUDITOR = SweepRole(prompt=str(Path(__file__).parent / 'auditor.md'), triggers=[NoKeep()], timeout=1800)
```

Register both in the package's `pyproject.toml`, and install the package in the environment of `piloop`:

```text
[project.entry-points."piloop.triggers"]
no_keep = "my_package:NoKeep"

[project.entry-points."piloop.roles"]
auditor = "my_package:AUDITOR"
```

Any project can then use `{ kind = "no_keep", hours = 12 }` in the triggers of a role, and gets the `auditor` role at
its next `piloop init`.

## Triggers

### The contract

A trigger is an entry of `[roles.<name>] triggers`: `{ kind = "<trigger>", <parameter> = <value> }`. On each tick,
for each sweeping role without a pending request, the daemon calls `fire(tick)` of each trigger of the role, in the
order of the list. It returns a `Fire` (the reason, how many agents, the events of the first one) or None. A trigger
reads with `tick` and writes nothing. A trigger with `ON_STOP` fires only on the tick that stops the campaign.

### Built in

{/* Generated by scripts/gen_docs.py: triggers. Do not edit this part: run `make docs`. */}

| Trigger | Fires when | Parameters |
|---|---|---|
| `anomaly` | The daemon detected an incident that no agent of the project got yet. The agent gets it to investigate. | none |
| `cron` | The role's `interval` passed since the start of its last routine agent, one that got no anomaly. | none |
| `seed` | A seed was filed after the role's latest agent started, and a slot of the role is free. | none |
| `low_water` | The backlog of runnable ideas is shorter than its target, and there is a reason to sweep now. | `buffer` |
| `stopped` | The campaign stopped (`[stop]`). It fires once, on the tick that stops the campaign. | none |
| `sql` | A query on the piloop database returns at least one row. | `when` |

{/* End of the generated part: triggers. */}

### Define your own

A `sql` trigger needs no code: its query fires the role when it returns a row ([Define a role](#define-a-role)). A
trigger with code of its own comes from a package, in the `piloop.triggers` group: see the `no_keep` trigger
[above](#define-your-own-in-a-package).

## Runtimes

### The contract

A runtime is where an agent runs. [Runtimes](/concepts/runtimes) explains what a runtime does for the user. The daemon
and the CLI depend only on the `Runtime` protocol in `piloop/runtime/__init__.py`:

{/* Generated by scripts/gen_docs.py: runtime-protocol. Do not edit this part: run `make docs`. */}

| Method | What it does |
|---|---|
| `start(spec)` | Start the agent from a `WorkerSpec` (argv, first prompt, working directory) and return once it runs. A failure leaves nothing running. A runtime that can show what the worker was stuck on raises `StartFailed`. |
| `wait(handle, timeout)` | Block until the agent is finished or gone. After `timeout` seconds, kill it and return `timed_out`. |
| `status(handle)` | Return the current state without waiting. |
| `session_id(handle)` | Return the harness's session id once the agent reports it, or None when the runtime cannot learn it. |
| `jobs(handle)` | Return `<pid> <command line>` for each job the agent started that still runs. Empty when unknown. |
| `prompt(handle, text)` | Queue a message for the agent's next turn. It never cuts the turn in progress short. An idle agent takes it at once. Raise `NotSteerable` when the runtime cannot deliver it (a harness that cannot continue its session, an ended agent, a dialog). |
| `read(handle, lines)` | Return the recent output as plain text. |
| `kill(handle)` | Stop the agent and what it left running, and release its resources. |
| `focus(handle)` | Bring the agent to the front of the runtime's own view, and return what was done. `enter` in `piloop watch` calls it. Raise `NotAttachable` when the runtime has no view of its own, and `RuntimeFailure` when it fails. |
| `attach(handle)` | Show the agent in this terminal, and return what was done. `piloop attach` calls it. It may replace this process, for example with the client of a terminal multiplexer. Raise `NotAttachable` when the runtime cannot show the agent, and `RuntimeFailure` when it fails. |
| `view(handle)` (class method) | Return where you can see the agent, in a few words (`tab w7:t3`), or None when there is no such place. `piloop status` and `piloop watch` show it. It reads only the handle, so it runs nothing. |
| `checks(executables)` (class method) | Check that the runtime can run agents on this machine. `piloop doctor` shows the result. `executables` are the programs of the harnesses that the projects of this runtime launch. Read only: start nothing. |

{/* End of the generated part: runtime-protocol. */}

A runtime class also has two class attributes, which piloop reads before it constructs the runtime:

- `kind`: the name of the runtime. It is the name of its entry point, the value of `runtime` in `piloop.toml` and the
  value of `workers.runtime`.
- `invocation`: the argument list of a harness that the runtime starts. `headless` is the argv for a process without a
  terminal, with the first prompt in it. `interactive` is the argv for a session in a terminal, and the runtime types
  the first prompt after the start.

The constructor takes the project's name and path. A failure that the runtime reports is a `RuntimeFailure`, and the
CLI shows its message. No caller checks the name of a runtime: a new runtime gets `piloop attach`, `piloop prompt`,
`piloop doctor` and `piloop watch` from its methods.

### Define your own

A package adds a runtime with an entry point in the `piloop.runtimes` group. [Add a runtime](/concepts/runtimes#add-a-runtime)
has an example: a runtime that starts each agent as `subprocess` does, at a lower CPU priority. A project then sets
`runtime = "<kind>"`, or a role sets it in its own table.

## Storage backends

### The contract

The artifact store keeps its blobs in `$PILOOP_HOME/store` and can mirror them to a remote. `[storage.remote]` in
`$PILOOP_HOME/config.toml` picks the remote's backend by `kind`, and the backend owns every other key of that table.
The keys of `[storage]` itself, such as `evict_after_days` and `min_free_gb`, are shared by every backend.
A remote stores whole objects by key. The store never lists, deletes or changes an object. A remote has:

- `url`: one spelling of where it puts objects, without a trailing `/`. The store records it at its first upload, and
  it refuses to open later with another `url`.
- `upload(key, path)`: store the file at `path` under `key`, streaming it. Uploading a key again is harmless.
- `download(key, path) -> bool`: write the object under `key` to `path`, streaming it. Return `False`, and write no
  file, when there is no such object. Raise on any other failure.
- `has(key) -> bool`: whether an object is stored under `key`.

### Built in

|---|---|---|
| `s3` | A bucket and prefix, and the storage class of each blob. | `url`, `storage_class`, `standard_below` |
| `gcs` | A bucket, a prefix in it, and the storage class of each blob. | `bucket`, `prefix`, `storage_class`, `project`, `credentials_file` |

{/* End of the generated part: remotes. */}

The [configuration reference](/reference/configuration) shows the same store with each backend.

### Define your own

A backend is two classes. A settings model subclasses `piloop.store.RemoteConfig`. Its `kind` is a literal, its
other fields are the keys of `[storage.remote]`, and its `open()` returns the remote. This backend mirrors the store
to a directory, for example a network share:

```python
import shutil
from pathlib import Path
from typing import Literal

from piloop.store import Remote, RemoteConfig


class ShareConfig(RemoteConfig):
    """``[storage.remote]`` with ``kind = "share"``: a mounted directory."""

    kind: Literal['share'] = 'share'
    root: Path
    """The directory that the objects go under."""

    def open(self) -> Remote:
        return Share(self.root)


class Share:
    def __init__(self, root: Path) -> None:
        self.root = root
        self.url = f'file://{root}'.rstrip('/')

    def upload(self, key: str, path: Path) -> None:
        target = self.root / key
        target.parent.mkdir(parents=True, exist_ok=True)
        shutil.copyfile(path, target)

    def download(self, key: str, path: Path) -> bool:
        if not (self.root / key).is_file():
            return False
        shutil.copyfile(self.root / key, path)
        return True

    def has(self, key: str) -> bool:
        return (self.root / key).is_file()
```

Register the settings model with an entry point in the `piloop.stores` group. The name of the entry point is the
`kind`:

```text
[project.entry-points."piloop.stores"]
share = "my_package:ShareConfig"
```

Install the package in the environment of `piloop`, then select the backend in `config.toml`:

```text
[storage.remote]
kind = "share"
root = "/mnt/archive/piloop"
```

piloop checks the table against `ShareConfig` when it opens the store: `piloop serve`, `piloop restore` and
`piloop store` fail on a key that the model does not have. A name that a built-in backend has already, or an entry
point that does not name a `RemoteConfig` subclass, is an error that names the entry point.

#### Test a backend

`piloop.store.contract.check_remote` runs the contract against a remote: missing keys, an upload and a download, and
a store that mirrors to the remote and keeps nothing local. It raises `ContractBroken` with the rule that failed.
piloop's own tests run it against `s3` and `gcs`. Run it in the tests of your package, against a scratch location:

```python
from pathlib import Path

from piloop.store.contract import check_remote

from my_package import ShareConfig


def test_the_share_keeps_the_contract(tmp_path: Path) -> None:
    check_remote(ShareConfig(root=tmp_path / 'share').open(), tmp_path / 'scratch')
```

It writes under `piloop-contract/<random>/`, and the contract has no delete, so point it at a bucket or a folder that
you can empty.

## Harnesses

### The contract

A harness is a coding agent CLI. A `[harness.<name>]` table in `piloop.toml` says how to start it: the executable, the
argv for a session in a terminal (`interactive`) and for a process without one (`headless`), and the startup dialogs to
accept. A runtime starts one of the two argument lists: its invocation. piloop fills in placeholders such as `{model}`,
`{session_id}`, `{cwd}` and `{prompt}`. The [configuration reference](/reference/configuration#harness) has every key.

### Built in

The built-in harnesses are definitions of the same kind, so a project can override any key of them. An override that
leaves out `busy_screens`, `failed_turn_screens` or `queue_key` keeps those of the built-in harness with the same
`executable`.

{/* Generated by scripts/gen_docs.py: harnesses. Do not edit this part: run `make docs`. */}

| Harness | Executable | Usage reader | MCP renderer | MCP servers, interactive | MCP servers, headless |
|---|---|---|---|---|---|
| `pi` | `pi` | `jsonl` (tally `pi`) | `pi` | no | yes |
| `claude` | `claude` | `jsonl` (tally `claude`) | `claude` | yes | yes |
| `codex` | `codex` | `jsonl` (tally `codex`) | `codex` | yes | yes |

{/* End of the generated part: harnesses. */}

### Define your own

Add a table with a new name, and put the name in `harnesses` or in a role's `harnesses`:

```toml
harnesses = ["claude", "mycli"]
model = { claude = "claude-opus-5-5", mycli = "my-model" }

[harness.mycli]
executable = "mycli"
headless = ["--model", "{model}", "{prompt}"]
```

To record its tokens and to give it MCP servers, it names a usage reader and an MCP renderer of the
[built-in ones](#usage-readers-and-mcp-renderers). A package cannot add a harness: a harness is configuration.

## MCP servers

### The contract

An `[mcp.<name>]` table defines an MCP server once, and `[roles.<name>] mcp` gives it to the agents of a role. piloop
writes it in the format of each harness, and passes API keys only as environment variables. A server is either
streamable HTTP (`url`) or stdio (`command`):

{/* Generated by scripts/gen_docs.py: mcp-keys. Do not edit this part: run `make docs`. */}

| Key | Meaning |
|---|---|
| `url` | The URL of a streamable HTTP server. SSE is not supported, because Codex and pi reject it. |
| `headers_env` | HTTP only. Maps each header name to the environment variable whose value is sent in it, for example `{ "x-api-key" = "EXA_API_KEY" }`. |
| `bearer_token_env` | HTTP only. The environment variable whose value is sent as `Authorization: Bearer <value>`. |
| `command` | The command (argv) of a stdio server, for example `["python3", "/path/to/server.py"]`. |
| `env` | stdio only. The environment variables that the server reads, for example `["XAI_API_KEY"]`. |

{/* End of the generated part: mcp-keys. */}

### Built in

piloop has no built-in MCP server. Its repo has one that you can run: `scripts/xai_search_mcp.py`, an X search for the
scout.

### Define your own

```toml
[mcp.exa]
url = "https://mcp.exa.ai/mcp"
headers_env = { "x-api-key" = "EXA_API_KEY" }

[roles.research]
mcp = ["exa"]
```

[MCP servers](/guides/mcp-servers) has the details, and what each harness gets.

## The evaluate command

### The contract

The evaluate command is the contract between piloop and your project. The daemon runs it in a clean worktree of each
commit. The command must:

- print one line `METRIC <name>=<value>` on stdout for each metric in `piloop.toml`;
- exit with status 0, within `evaluate_timeout` seconds. Otherwise the candidate is a `crash`.

When the daemon sets `PILOOP_UNITS_FILE`, the command can also write the result of each unit (each example, record or
file) to that path, so that the verdict can use a paired bootstrap. See
[The evaluate command](/concepts/projects#the-evaluate-command) and [per-unit results](/concepts/projects#per-unit-results).

### Built in

piloop has no evaluate command of its own: each project has its own. `piloop init` writes a stub `evaluate.py` to edit,
and `piloop init --example <name>` writes a bundled example project with a working one:

{/* Generated by scripts/gen_docs.py: evaluate-examples. Do not edit this part: run `make docs`. */}

| Example | Goal | Data it downloads |
|---|---|---|
| `enwik8` | enwik8: compress the first 10 MB of Wikipedia | `data/enwik8.zip` |
| `titanic-tracks` | Titanic survival: accurate, and cheap to run | `data/train.csv` |

{/* End of the generated part: evaluate-examples. */}

### Define your own

Set `evaluate` to the argv of your command:

```toml
evaluate = ["uv", "run", "python", "evaluate.py"]
evaluate_timeout = 600
```

```python
import subprocess

lines = subprocess.run(["python", "solve.py", "--check"], capture_output=True, text=True, check=True).stdout
print(f"METRIC score={lines.count('ok')}")
```

## Stop conditions

### The contract

`[stop]` ends the campaign when one of its conditions holds. The daemon checks them on every tick, before it requests
anything. [Cost and spend limits](/concepts/cost#stop-conditions) says what happens then.

### Built in

{/* Generated by scripts/gen_docs.py: stop. Do not edit this part: run `make docs`. */}

| Key | Meaning |
|---|---|
| `target` | Stop when the primary metric at the head (the latest keep on the trunk) reaches this value, in its direction. Only for a project with one track. |
| `max_runs` | Stop after this many worker runs, once none of them is queued, running or being scored. A run counts while it is queued, running or being scored, so piloop never starts more runs than this. A finished run counts when it has a candidate that is measured or waits for its measurement. A run with no commit or only `Piloop-Eval: skip` commits does not count, and piloop starts another run in its place. A run that a daemon stop, a daemon crash or a campaign stop ended does not count either. `[spend]` and `max_tokens` limit what those runs cost. |

| `max_tokens` | Stop when all the agents of the project together spent this many tokens (the `total` of `workers.usage`), summed over the agents that ended. |
| `plateau` | Stop after this many finished runs in a row without a new `keep` candidate. Every finished run counts, also one with no commit or only `Piloop-Eval: skip` commits: such runs make no progress either. A run that a daemon stop, a daemon crash or a campaign stop ended does not count. |

### Define your own

You cannot add a stop condition today. Combine the built-in ones in `[stop]`:

```toml
[stop]
max_hours = 24
plateau = 30
```

You can change what piloop does in two ways: with configuration, or with a plugin.

These words have one meaning on this page:

- A **plugin** is a Python package that you install next to piloop.
- A **capability** is a part of piloop that a plugin can replace or add to, for example the runtime that starts the
  agents.
- A **provider** is one implementation of a capability. It has a name, for example the runtime `subprocess`.
- A **built-in** provider is one that piloop includes. Each capability has at least one.
- The configuration selects a provider by its name. A plugin adds providers.

A plugin imports what it needs of piloop from one module, `piloop.capabilities`: each capability, the types of its
contract, and its built-in providers. The names on this page are names in that module:

```python
from piloop.capabilities import BOOTSTRAP, Case, Judgement, Outcome
```

Each example plugin on this page is a package in
[`examples/plugins/`](https://github.com/hiloopai/piloop/tree/main/examples/plugins). piloop's tests install each
one and select it in the configuration.

Each decision that piloop makes is a capability, for example the verdict rule that decides which candidates to
keep. You can replace the built-in provider of a capability. Some parts of piloop are not capabilities, and you cannot
replace them: the [overview](/architecture/overview#what-you-can-replace) lists them.

A plugin can also do two more things:

- [Call a built-in provider](#call-a-built-in-provider) and change one part of its answer.
- [Let other plugins extend it](#let-other-plugins-extend-your-plugin): it declares a capability of its own, and
  other plugins add providers to it.

## Runtimes

piloop starts each agent through a runtime. The runtime starts the agent's process. piloop then asks the runtime if
the agent still works, sends messages to the agent through it, and stops the agent through it.

### Example: run the agents under `nice`

This runtime starts each agent as the built-in runtime `subprocess` does, but with a lower CPU priority:

<ExampleNiceRuntime />

Install it next to piloop, then select it in `piloop.toml` and run `piloop init .`:

```bash
uv tool install piloop --with ./examples/plugins/nice-runtime
piloop plugins
```

```toml
runtime = "nice"
```

A role can select its own: `[roles.research] runtime = "herdr"`. `[runtimes.nice]` in `config.toml` holds the
runtime's settings.

### The contract

A runtime is a class with the methods of the `Runtime` protocol, and two class attributes: `kind`, its name (the name
of its entry point), and `invocation`, which argument list of a harness it starts (`headless` with the first prompt
in it, or `interactive`, a terminal session that the runtime types the prompt into). Its constructor takes the
campaign's name and path. It reports a failure as a `RuntimeFailure`. `piloop attach`, `prompt`, `doctor` and `watch`
call its methods, so a new runtime gets them at once. [Runtimes](/concepts/runtimes) says what a runtime does for
you.

## Storage backends

piloop keeps the files of its artifact store in `$PILOOP_HOME/store`. If you select a storage backend, piloop also
copies each file to a remote place. The backend uploads a file, downloads a file, and says if a file is there.

### Example: mirror the store to a directory

This backend copies the files to a directory, for example a network share that is mounted on the machine:

<ExampleDirStore />

Install it, then select it in `$PILOOP_HOME/config.toml` and restart the daemon (`piloop restart`):

```toml
[storage.backend]
kind = "dir"
root = "/mnt/archive/piloop"
```

### The contract

The artifact store keeps its blobs in `$PILOOP_HOME/store` and can mirror them to a storage backend. A backend is a
settings model, a subclass of `StorageBackendConfig`: its `kind` is the name of its entry point, its fields are the
other keys of `[storage.backend]`, and its `open()` returns the `StorageBackend`. That one stores
whole objects by key, and the store never lists, deletes or changes one:

- `url`: where it puts objects, without a trailing `/`. The store records it at its first upload, and refuses to open
  later with another one.
- `upload(key, path)`: store the file, streaming it. Uploading a key again is harmless.
- `download(key, path) -> bool`: write the object to `path`; `False`, and no file, when there is none.
- `has(key) -> bool`: whether an object is stored under `key`.

`check_storage_backend(backend, scratch)` runs the contract against a backend, as piloop's tests
do with the example. It writes under `piloop-contract/<random>/` and never deletes, so point it at a folder that you can
empty.

## Pure plugins

A **pure** capability gets data and returns data. Its provider does not read the database, files or other parts of
piloop: piloop gives it all that it needs as arguments. A pure provider imports only the Python standard library and,
from `piloop.capabilities`, the **contract** of its capability (the types that the provider gets and returns) and the
built-in providers that it calls. Because of
this, piloop can later run the same provider in another process, or as a WebAssembly component.

The [verdict rules](#verdict-rules) and the [stop rules](#stop-conditions) are pure capabilities, and their examples
are pure plugins. You select the provider of a pure capability with a table in `piloop.toml`. `provider` is its name. The other keys of the table are
the provider's **parameters**. piloop checks them against the provider's `Parameters` type when it loads
`piloop.toml`:

```text
[plugins.verdict_rule]
provider = "min_gain"
min_gain = 100
```

### The contract

The contract of a pure capability is a Python protocol that has only methods. The arguments and the return value of
each method are data:

- Data is `str`, `int`, `float`, `bool`, `bytes`, an enum, a dataclass or a pydantic model of data, `list`, `tuple`,
  `dict`, and unions of these.
- A database session, a file, a function or another class is not data.
- No part of a type can be of any type: no `Any`, no `object`, no model that allows extra fields.
- No type can contain itself.

These are the rules of WIT, the interface language of WebAssembly components. A provider returns an error as a
value, a case of a union of records. It does not raise an exception. The entry point of a pure provider names an
instance, not a class. piloop checks that the instance has the methods of the contract, with the same argument
names.

### Data that costs queries

Some data costs database queries to get. A pure provider that needs such data does not query. It names the data
first, and piloop gets only that data. Then the provider decides from it.

#### Example: a stop rule that names the facts it needs

The example stop rule `after_keeps` stops the campaign after a number of keeps. It needs the fact `keeps`. It leaves
the cost limits to the built-in rule `limits`, so it also names the facts that `limits` needs for them:

```python
class AfterKeeps:
    def reads(self, limits: Limits, parameters: str) -> list[Fact]:
        return [Fact.KEEPS, *LIMITS.reads(costs(limits), '{}')]  # 1. name the facts

    def check(self, case: StopCase) -> Go | Hold | Stop:  # 3. decide from those facts
        answer = LIMITS.check(replace(case, limits=costs(case.limits), parameters='{}'))
        keeps = case.progress.keeps
        if isinstance(answer, Hold) or keeps is None or keeps < Parameters(**json.loads(case.parameters)).keeps:
            return answer
        return Stop(f'after_keeps: {keeps} keeps')
```

`costs` keeps only `max_hours`, `max_tokens` and the `[spend]` limit. The full package is in
[Stop conditions](#example-end-the-campaign-after-a-number-of-keeps). With this `piloop.toml`:

```toml
[plugins.stop_rule]
provider = "after_keeps"
keeps = 3

[spend]
command = ["uv", "run", "scripts/spend.py"]
limit = 300
```

piloop does this on each tick:

1. It calls `reads`. The rule returns `[Fact.KEEPS, Fact.SPEND]`. No `max_hours` or `max_tokens` is set, so `limits`
   needs no other fact.
2. It counts the keeps and reads the spend. It does not count the runs, the hours or the tokens: no query runs for
   them, and they are `None` in `case.progress`.
3. It calls `check` with the limits, those two facts and the parameters. The rule holds while the spend is unknown or
   at its limit. Else it stops at 3 keeps. Else it goes on.
## Verdict rules

After piloop measures a candidate, it asks the verdict rule whether to keep the candidate. piloop gives the rule a
`Case`: the measurements of the candidate, the measurements of its bar, and the metrics that decide. The bar is the
candidate that this one must beat. The rule returns a `Judgement`: `keep`, `interesting`, `discard` or `crash`, and
a reason. piloop stores the verdict and the reason on the candidate.

The built-in rule is `bootstrap`. It keeps a candidate when the primary metric beats the bar with confidence and no
guardrail metric gets too much worse.

### Example: keep only a gain of a fixed size

This rule [calls the built-in rule](#call-a-built-in-provider) `bootstrap` and changes one thing: a keep whose gain is
below `min_gain` becomes `interesting`. `min_gain` is in the units of the primary metric:

<ExampleMinGain />

Install it next to piloop, then select it in `piloop.toml` and run `piloop init .`:

```bash
uv tool install piloop --with ./examples/plugins/min-gain
piloop plugins
```

```text
[plugins.verdict_rule]
provider = "min_gain"
min_gain = 100
```

`min_gain` is a parameter of the rule. piloop checks it against the rule's `Parameters` when it loads
`piloop.toml`. piloop then gives it to the rule in each `Case`, as JSON text.

### The contract

A verdict rule is a [pure](#pure-plugins) provider with one method: `decide(case: Case) -> Judgement`. Import the
types from `piloop.capabilities`.

- `Case.primary`: the primary metric of the candidate's track, as a `Criterion` (name, direction, margin, floor).
- `Case.guardrails`: the guardrail metrics, each a `Criterion`.
- `Case.confidence`: `confidence` in `piloop.toml`.
- `Case.candidate` and `Case.bar`: each a `Side`. A `Side` has a name for the reason (`candidate#73`), the mean of
  each metric, and the per-unit results of the metrics that have them.
- `Case.parameters`: the rule's parameters, as JSON text.
- `Judgement.verdict`: `keep`, `interesting`, `discard` or `crash`.
- `Judgement.reason`: the text that piloop stores and shows with the verdict.

A rule has no error case: it returns a verdict for every case.

The rule decides only the verdict. piloop does the rest, whatever the rule:

- It chooses the bar.
- It moves the head to a keep.
- It merges a keep onto the head when the head moved during the run.
- It adds `no-op` to the reason when the metrics equal those of the parent.
- It applies the `Piloop-Note` of a commit.

### Built in

`bootstrap` is the rule of a campaign without `[plugins.verdict_rule]`. [The verdict](/concepts/verdict#the-verdict)
describes it:

- The primary metric must beat the bar at the `confidence` level of a paired bootstrap.
- Each guardrail metric can get worse by at most its margin.
- No guardrail metric can pass its floor.

## Roles

### Example: a role in configuration

Add a table with a new name, a prompt file and at least one trigger. This role reads each new escalation in the inbox
and writes a plan for it, one agent at a time, in the campaign checkout:

```toml
[roles.planner]
prompt = "briefs/planner.md"
triggers = [
  { kind = "sql", when = "SELECT id FROM comments WHERE kind = 'escalation' AND acked_at IS NULL AND created_at > :since" },
]
workdir = "repo"
max_concurrent = 1
timeout = 1200
files = "seeds"
writes = ["comments(finding) on the escalation", "seeds via idea seed"]
```

Then write the prompt and store the config:

```bash
mkdir -p briefs
printf '# Planner\nFor each new escalation, write a finding with a plan of three steps.\n' > briefs/planner.md
piloop init .
```

The daemon now checks the query on each tick. When it returns a row, the daemon requests a `planner` agent, and
`piloop status` lists it as `planner#<agent session id>`. The agent signs its comments `planner#<agent session id>`.

### Example: a role that does runs

Add a table with a new name and `runs = true`. The role takes the implementer's defaults, so every other key is optional.
This role runs the ideas of the `speed` track with Claude, two at a time, and stops each agent after 10 minutes:

```toml
model = { pi = "anthropic/claude-opus-5-5", claude = "claude-opus-5-5" }

[roles.sprinter]
runs = true
takes = "track = 'speed'"
prompt = "briefs/sprinter.md"
harnesses = ["claude"]
max_concurrent = 2
timeout = 600

[roles.implementer]
takes = "track != 'speed'"
```

`takes` is an SQL condition on the `ideas` table, so it can select by any column: `priority`, `track`, `family`,
`harness`, or a subquery. Without `takes` on the implementer, the implementer also runs the `speed` ideas that wait for a free
`sprinter` slot. Write the prompt and store the config:

```bash
mkdir -p briefs
printf '# Sprinter\nMake the change that the idea names, measure it once, and commit.\n' > briefs/sprinter.md
piloop init .
```

The daemon queues each `speed` idea for a `sprinter` run. The run's agent signs `sprinter#<agent session id>`, its brief has
the idea and the starting point as an implementer's has, and its commits are scored and judged like an implementer's.
[Roles](/concepts/roles#define-a-role-that-does-runs) lists which rules apply to each role and which apply to every run.

### Example: a role and a trigger from a plugin

A plugin can add roles and triggers. This plugin adds a trigger, `no_keep`, that starts an agent when no candidate
was kept for some hours. It also adds a role, `auditor`, that uses this trigger:

```python
from datetime import timedelta
from pathlib import Path
from typing import Literal

from sqlalchemy import func, select

from piloop.capabilities import Fire, SweepRole, Tick, Trigger
from piloop.db.models import Candidate, Verdict, utcnow


class NoKeep(Trigger):
    """``no_keep``: no new keep for ``hours`` hours, once per agent of the role."""

    kind: Literal['no_keep'] = 'no_keep'
    hours: float = 6

    def fire(self, tick: Tick) -> Fire | None:
        keeps = select(func.max(Candidate.created_at)).where(
            Candidate.campaign_id == tick.campaign.id, Candidate.verdict == Verdict.KEEP
        )
        latest = tick.s.scalar(keeps) or tick.campaign.created_at
        started = tick.last.started_at if tick.last is not None else latest
        if utcnow() - max(latest, started) < timedelta(hours=self.hours):
            return None
        return Fire(f'no keep for {self.hours:g} hours')


AUDITOR = SweepRole(prompt=str(Path(__file__).parent / 'auditor.md'), triggers=[NoKeep()], timeout=1800)
```

```toml
[project.entry-points."piloop.triggers"]
no_keep = "my_package:NoKeep"

[project.entry-points."piloop.roles"]
auditor = "my_package:AUDITOR"
```

Any campaign can then use `{ kind = "no_keep", hours = 12 }` in the triggers of a role, and gets the `auditor` role,
with its table in `piloop.toml` over the package's defaults, at its next `piloop init`.

### The contract

A role is a table in `piloop.toml`: its prompt, when it starts (the run queue, or its triggers), where it works, how
(harnesses, models, MCP servers, timeout, concurrency) and what it may file. A role that does runs (`runs = true`)
takes ideas from the run queue, and its commits are scored and judged. A sweeping role starts on its triggers, and
nothing it commits is scored. A plugin's role is a `SweepRole` or an `ImplementerRole` with the defaults. [Roles](/concepts/roles) describes each key.

## Triggers

### Example

A `sql` trigger needs no code: its query fires the role when it returns a row, as the planner above. A trigger with
code of its own comes from a plugin: see `no_keep` above.

### The contract

A trigger is an entry of `[roles.<name>] triggers`: `{ kind = "<trigger>", <parameter> = <value> }`. A plugin's
trigger is a subclass of `Trigger`: its fields are its parameters. On each tick, for each sweeping role
without a pending request, the daemon calls `fire(tick)` of each trigger of the role in order. It returns a `Fire`
(the reason, how many agents) or None, and reads with `tick` (a `Tick`: the session, the campaign, the role and the
queries of the built-in triggers). The rows that it reads are the models of `piloop.db.models`, the
[data model](/architecture/data-model). A trigger with `ON_STOP` fires only on the tick that stops the
campaign.

### Example

### The contract

A harness is a coding agent CLI, and a `[harness.<name>]` table says how to start it: the executable, the argv with

## The evaluate command

### Example

```toml
evaluate = ["uv", "run", "python", "evaluate.py"]
evaluate_timeout = 600
```

```python
import subprocess

lines = subprocess.run(["python", "solve.py", "--check"], capture_output=True, text=True, check=True).stdout
```

### The contract

The daemon runs the command in a clean worktree of each commit. It prints one line `METRIC <name>=<value>` for each

## Stop conditions

On each tick (every 2 seconds by default), the daemon asks the stop rule of each active campaign whether the campaign
goes on, holds, or stops. piloop gives the rule a `StopCase`: the limits, the facts that the rule asked for, and the
rule's parameters. The rule returns one of three answers:

| Answer | What piloop does |
|---|---|
| `Go` | It starts what the campaign needs: runs, sweeps and evaluations. |
| `Hold(reason)` | It starts no agent and no evaluation for the campaign. Work that runs finishes, and piloop scores it. `piloop status` shows `launches held: <reason>`. |
| `Stop(reason)` | It stops the campaign. [Cost and spend limits](/concepts/cost#stop-conditions) says what a stop does. |

A hold is not a pause. piloop asks the rule again on each tick, and the hold ends when the rule answers `Go`. piloop
does not stop a paused campaign, but it holds one.

The built-in rule is `limits`. It holds the campaign while the spend of `[spend]` is unknown or at its limit. Else it
stops the campaign at the first limit of `[stop]` that the campaign reaches.

### Example: end the campaign after a number of keeps

This rule stops the campaign after `keeps` candidates are kept. It [calls the built-in rule](#call-a-built-in-provider)
`limits` for `max_hours` and `max_tokens` of `[stop]`, and for `[spend]`, so these limits still apply:

<ExampleStopAfterKeeps />

Install it next to piloop, then select it in `piloop.toml` and run `piloop init .`:

```bash
uv tool install piloop --with ./examples/plugins/stop-after-keeps
piloop plugins
```

```text
[plugins.stop_rule]
provider = "after_keeps"
keeps = 3
```

### The contract

A stop rule is a [pure](#pure-plugins) provider with two methods. Import the types from `piloop.capabilities`.

- `reads(limits, parameters) -> list[Fact]`: the facts that the rule needs. Most facts cost database queries on every
  tick, so piloop gets only these.
- `check(case: StopCase) -> Go | Hold | Stop`: the answer. `Hold` and `Stop` have a `reason`.

The facts are:

- `head`: the primary metric of the head.
- `runs`: the runs that count toward `max_runs`, and the runs that can still count.
- `hours`: the hours since the first run started, without the time that the campaign was paused.
- `tokens`: the tokens that the agents spent.
- `without_keep`: the runs since the last keep.
- `keeps`: the candidates of runs that are kept.
- `spend`: the spend in USD that the `[spend]` command printed last, and why its last run failed, if it failed.

A `StopCase` has the name and direction of the primary metric, the limits, the facts that the rule asked for, and
the rule's parameters as JSON text. The limits are the keys of `[stop]`, and `max_spend`, the `limit` of `[spend]`.

A stop that a person requests (`piloop campaign stop`) stops the campaign whatever the rule answers, also when the
rule holds it. The closing review of that stop then follows `closing_review` of `[spend]`
([Cost and spend limits](/concepts/cost#spend-outside-piloop)).

Only the stop rule holds the campaign at the `limit` of `[spend]`. When `piloop.toml` has a `[spend]` table, the
rule must ask for `spend`. If it does not, piloop refuses the configuration.

### Built in

`limits` is the rule of a campaign without `[plugins.stop_rule]`:

1. It holds the campaign while the `[spend]` command has not printed a spend yet, while its last run failed, or while
   the spend is at its `limit` or above.
2. Else it stops the campaign at the first limit of `[stop]` that the campaign reaches.

The hold comes first: a limit of `[stop]` does not stop a held campaign.

```toml
[stop]
max_hours = 24
plateau = 30
```

## Call a built-in provider

A provider of a plugin can call a built-in provider, and then change one part of the answer. The rest of the answer
stays the same as the built-in provider's.

### Example: the built-in verdict rule, with a minimum gain

The verdict rule `min_gain` (in [Verdict rules](#verdict-rules)) does this:

1. piloop calls `min_gain` with a `Case`: the measurements of a candidate and of its bar.
2. `min_gain` calls the built-in rule `bootstrap` with the same `Case`. `bootstrap` returns a `Judgement`: a verdict
   and a reason.
3. If the verdict is `keep` and the gain is below `min_gain`, `min_gain` returns `interesting` with the same reason
   and a note. Otherwise it returns the `Judgement` of `bootstrap`.

```python
from piloop.capabilities import BOOTSTRAP, Case, Judgement, Outcome


class MinGain:
    def decide(self, case: Case) -> Judgement:
        judged = BOOTSTRAP.decide(case)  # the built-in rule's verdict and reason
        if judged.verdict is Outcome.KEEP and gain(case) < least(case):
            return Judgement(Outcome.INTERESTING, judged.reason + '; the gain is below min_gain')
        return judged
```

`gain` and `least` are short helpers. The full rule is in the [example](#example-keep-only-a-gain-of-a-fixed-size).

## Let other plugins extend your plugin

A plugin can let other plugins extend it. It declares a capability: a named kind of provider. Then it calls the
providers of that capability. Other plugins add providers to the capability, and piloop loads them.

### Example: verdict checks

Two example plugins work together:

- `verdict-checks` declares the capability `verdict check`. A verdict check looks at a candidate that `bootstrap`
  keeps, and can refuse it. `verdict-checks` also adds the verdict rule `checked`. This rule calls `bootstrap`, then
  each verdict check that its parameter `checks` names. When a check refuses the candidate, `checked` returns
  `interesting` with the reason of the check.

### How to declare a capability

1. Make a `Capability`, or a `PureCapability` with its contract. Import both from `piloop.capabilities`. Give it a name
   (`verdict check`) and an entry point group for its providers (`piloop_verdict_checks.checks`).
2. Add an entry point in `piloop.capabilities` that names it. The name of the entry point is the name of the concept
   (`verdict_check`).
3. Call a provider with `get(name)`. piloop loads and checks all the providers when you first call `get`.
4. Check the names of the providers when the configuration loads, for example in your `Parameters`. `get` fails on a
   name that no provider has, and the error lists the names that exist.

`piloop plugins` and `piloop doctor` list your capability and its providers. piloop itself calls only its own
capabilities. A provider that calls another capability runs in the process of piloop.

## How piloop loads plugins

The **plugin host** is the part of piloop that finds, checks and loads plugins (`piloop.plugins.host`).

- **Capabilities.** An entry point in `piloop.capabilities` declares a capability. piloop declares its own
  capabilities in this way. A plugin can also declare one
  ([Let other plugins extend your plugin](#let-other-plugins-extend-your-plugin)).
- **Entry points.** A plugin adds a provider with an entry point in the group of a capability, for example
  `piloop.runtimes`. The name of the entry point is the name of the provider. piloop's own providers are entry points
  of the `piloop` package, in the same groups, so piloop loads them as it loads a plugin's.
- **All or nothing.** piloop loads every provider of a capability and checks each one. Then it registers all of them,
  or none.
- **Before the daemon starts.** The daemon loads each capability that it uses before it opens the database. It does
  not start when an entry point does not import, names an object of the wrong type, or uses a name that another
  provider has. It also does not start when `config.toml` selects a provider that does not exist.
- **The same checks elsewhere.** `piloop serve --check`, `piloop doctor` and `piloop plugins` do the same checks.
  `piloop restart` and `piloop upgrade` do them first, and keep the daemon running if it would not start again.
  A broken storage backend that nothing selects is only a warning.
- **Selection.** Each capability says where the configuration selects its provider. The runtime and the storage
  backend have their own keys. A new capability uses a table in `piloop.toml`: `provider` is the name of the provider,
  and the other keys are its parameters. If no provider has that name, the error names the key and lists the names
  that exist.
- **Versions.** An entry point group is one version of a contract. An incompatible change to a contract gets a new
  group.
- **Two kinds of contract.** A provider of the runtimes, the storage backends, the triggers or the roles can get live
  objects of piloop: processes, files, a database session. A provider of a pure capability gets data only. piloop
  loads, selects, lists and unloads both kinds in the same way.

You can change what piloop does in two ways: with configuration, or with a plugin.

These words have one meaning on this page:

- A **plugin** is a Python package that you install next to piloop.
- A **capability** is a part of piloop that a plugin can replace or add to, for example the runtime that starts the
  agents.
- A **provider** is one implementation of a capability. It has a name, for example the runtime `subprocess`.
- A **built-in** provider is one that piloop includes. Each capability has at least one.
- The configuration selects a provider by its name. A plugin adds providers.

Each example plugin on this page is a package in
[`examples/plugins/`](https://github.com/hiloopai/piloop/tree/main/examples/plugins). piloop's tests install each
one and select it in the configuration.

## Runtimes

piloop starts each agent through a runtime. The runtime starts the agent's process. piloop then asks the runtime if
the agent still works, sends messages to the agent through it, and stops the agent through it.

### Example: run the agents under `nice`

This runtime starts each agent as the built-in runtime `subprocess` does, but with a lower CPU priority:

<ExampleNiceRuntime />

Install it next to piloop, then select it in `piloop.toml` and run `piloop init .`:

```bash
uv tool install piloop --with ./examples/plugins/nice-runtime
piloop plugins
```

```toml
runtime = "nice"
```

A role can select its own: `[roles.research] runtime = "herdr"`. `[runtimes.nice]` in `config.toml` holds the
runtime's settings.

### The contract

A runtime is a class with the methods of the `Runtime` protocol, and two class attributes: `kind`, its name (the name
of its entry point), and `invocation`, which argument list of a harness it starts (`headless` with the first prompt
in it, or `interactive`, a terminal session that the runtime types the prompt into). Its constructor takes the
project's name and path. It reports a failure as a `RuntimeFailure`. `piloop attach`, `prompt`, `doctor` and `watch`
call its methods, so a new runtime gets them at once. [Runtimes](/concepts/runtimes) says what a runtime does for
you.

## Storage backends

piloop keeps the files of its artifact store in `$PILOOP_HOME/store`. If you select a storage backend, piloop also
copies each file to a remote place. The backend uploads a file, downloads a file, and says if a file is there.

### Example: mirror the store to a directory

This backend copies the files to a directory, for example a network share that is mounted on the machine:

<ExampleDirStore />

Install it, then select it in `$PILOOP_HOME/config.toml` and restart the daemon (`piloop restart`):

```toml
[storage.remote]
kind = "dir"
root = "/mnt/archive/piloop"
```

### The contract

The artifact store keeps its blobs in `$PILOOP_HOME/store` and can mirror them to a remote. A backend is a settings
model, a subclass of `piloop.store.RemoteConfig`: its `kind` is the name of its entry point, its fields are the other
keys of `[storage.remote]`, and its `open()` returns the remote. A remote stores whole objects by key, and the store
never lists, deletes or changes one:

- `url`: where it puts objects, without a trailing `/`. The store records it at its first upload, and refuses to open
  later with another one.
- `upload(key, path)`: store the file, streaming it. Uploading a key again is harmless.
- `download(key, path) -> bool`: write the object to `path`; `False`, and no file, when there is none.
- `has(key) -> bool`: whether an object is stored under `key`.

`piloop.store.contract.check_remote(remote, scratch)` runs the contract against a remote, as piloop's tests do with
the example. It writes under `piloop-contract/<random>/` and never deletes, so point it at a folder that you can
empty.

## Pure plugins

### Example: pick the next idea by priority

<ExamplePickByPriority />

A **pure** capability gets data and returns data. Its provider does not read the database, files or other parts of
piloop: piloop gives it all that it needs as arguments. A pure provider imports only the Python standard library and
the **contract** of its capability, the module that defines the types that the provider gets and returns. Because of
this, piloop can later run the same provider in another process, or as a WebAssembly component.

piloop has no pure capability yet: its tests declare one for this example. You select the provider of a pure
capability with a table in `piloop.toml`. `provider` is its name. The other keys of the table are the provider's
**parameters**, and piloop checks them against the provider's `Parameters` type when it loads `piloop.toml`:

```text
[plugins.idea_picker]
provider = "by_priority"
```

### The contract

The contract of a pure capability is a Python protocol that has only methods. The arguments and the return value of
each method are data:

- Data is `str`, `int`, `float`, `bool`, `bytes`, an enum, a dataclass or a pydantic model of data, `list`, `tuple`,
  `dict`, and unions of these.
- A database session, a file, a function or another class is not data.
- No part of a type can be of any type: no `Any`, no `object`, no model that allows extra fields.
- No type can contain itself.

These are the rules of WIT, the interface language of WebAssembly components. A provider returns an error as a
value, a case of a union of records. It does not raise an exception. The entry point of a pure provider names an
instance, not a class. piloop checks that the instance has the methods of the contract, with the same argument
names.

## Roles

### Example: a role in configuration

Add a table with a new name, a prompt file and at least one trigger. This role reads each new escalation in the inbox
and writes a plan for it, one agent at a time, in the project checkout:

```toml
[roles.planner]
prompt = "briefs/planner.md"
triggers = [
  { kind = "sql", when = "SELECT id FROM comments WHERE kind = 'escalation' AND acked_at IS NULL AND created_at > :since" },
]
workdir = "project"
max_concurrent = 1
timeout = 1200
files = "seeds"
writes = ["comments(finding) on the escalation", "seeds via idea seed"]
```

Then write the prompt and store the config:

```bash
mkdir -p briefs
printf '# Planner\nFor each new escalation, write a finding with a plan of three steps.\n' > briefs/planner.md
piloop init .
```

The daemon now checks the query on each tick. When it returns a row, the daemon requests a `planner` agent, and
`piloop status` lists it as `planner#<worker id>`. The agent signs its comments `planner#<worker id>`.

### Example: a role that does runs

Add a table with a new name and `runs = true`. The role takes the worker's defaults, so every other key is optional.
This role runs the ideas of the `speed` track with Claude, two at a time, and stops each agent after 10 minutes:

```toml
model = { pi = "anthropic/claude-opus-5-5", claude = "claude-opus-5-5" }

[roles.sprinter]
runs = true
takes = "track = 'speed'"
prompt = "briefs/sprinter.md"
harnesses = ["claude"]
max_concurrent = 2
timeout = 600

[roles.worker]
takes = "track != 'speed'"
```

`takes` is an SQL condition on the `ideas` table, so it can select by any column: `priority`, `track`, `family`,
`harness`, or a subquery. Without `takes` on the worker, the worker also runs the `speed` ideas that wait for a free
`sprinter` slot. Write the prompt and store the config:

```bash
mkdir -p briefs
printf '# Sprinter\nMake the change that the idea names, measure it once, and commit.\n' > briefs/sprinter.md
piloop init .
```

The daemon queues each `speed` idea for a `sprinter` run. The run's agent signs `sprinter#<worker id>`, its brief has
the idea and the starting point as a worker's has, and its commits are scored and judged like a worker's.
[Roles](/concepts/roles#define-a-role-that-does-runs) lists which rules apply to each role and which apply to every run.

### Example: a role and a trigger from a plugin

A plugin can add roles and triggers. This plugin adds a trigger, `no_keep`, that starts an agent when no candidate
was kept for some hours. It also adds a role, `auditor`, that uses this trigger:

```python
from datetime import timedelta
from pathlib import Path
from typing import Literal

from sqlalchemy import func, select

from piloop.config import SweepRole
from piloop.db.models import Candidate, Verdict, utcnow
from piloop.triggers import Fire, Tick, Trigger


class NoKeep(Trigger):
    """``no_keep``: no new keep for ``hours`` hours, once per agent of the role."""

    kind: Literal['no_keep'] = 'no_keep'
    hours: float = 6

    def fire(self, tick: Tick) -> Fire | None:
        keeps = select(func.max(Candidate.created_at)).where(
            Candidate.project_id == tick.project.id, Candidate.verdict == Verdict.KEEP
        )
        latest = tick.s.scalar(keeps) or tick.project.created_at
        started = tick.last.started_at if tick.last is not None else latest
        if utcnow() - max(latest, started) < timedelta(hours=self.hours):
            return None
        return Fire(f'no keep for {self.hours:g} hours')


AUDITOR = SweepRole(prompt=str(Path(__file__).parent / 'auditor.md'), triggers=[NoKeep()], timeout=1800)
```

```text
[project.entry-points."piloop.triggers"]
no_keep = "my_package:NoKeep"

[project.entry-points."piloop.roles"]
auditor = "my_package:AUDITOR"
```

Any project can then use `{ kind = "no_keep", hours = 12 }` in the triggers of a role, and gets the `auditor` role,
with its table in `piloop.toml` over the package's defaults, at its next `piloop init`.

### The contract

A role is a table in `piloop.toml`: its prompt, when it starts (the run queue, or its triggers), where it works, how
(harnesses, models, MCP servers, timeout, concurrency) and what it may file. A role that does runs (`runs = true`)
takes ideas from the run queue, and its commits are scored and judged. A sweeping role starts on its triggers, and
nothing it commits is scored. A plugin's role is a `piloop.config.SweepRole` or `piloop.config.WorkerRole` with the
defaults. [Roles](/concepts/roles) describes each key.

## Triggers

### Example

A `sql` trigger needs no code: its query fires the role when it returns a row, as the planner above. A trigger with
code of its own comes from a plugin: see `no_keep` above.

### The contract

A trigger is an entry of `[roles.<name>] triggers`: `{ kind = "<trigger>", <parameter> = <value> }`. A plugin's
trigger is a subclass of `piloop.triggers.Trigger`: its fields are its parameters. On each tick, for each sweeping role
without a pending request, the daemon calls `fire(tick)` of each trigger of the role in order. It returns a `Fire`
(the reason, how many agents) or None, and reads with `tick` (`piloop.triggers.Tick`: the session, the project, the
role and the queries of the built-in triggers). A trigger with `ON_STOP` fires only on the tick that stops the
campaign.

## Harnesses

### Example

```toml
harnesses = ["claude", "mycli"]
model = { claude = "claude-opus-5-5", mycli = "my-model" }

[harness.mycli]
executable = "mycli"
headless = ["--model", "{model}", "{prompt}"]
```

### The contract

A harness is a coding agent CLI, and a `[harness.<name>]` table says how to start it: the executable, the argv with
a terminal (`interactive`) and without one (`headless`), and the startup dialogs to accept. piloop fills in
`{model}`, `{session_id}`, `{cwd}` and `{prompt}`. To record its tokens and give it MCP servers, it names one of the
[built-in readers and renderers](#usage-readers-and-mcp-renderers). The
[configuration reference](/reference/configuration#harness) has every key.

### Built in

A project can override any key of a built-in harness. An override without `busy_screens`, `failed_turn_screens` or
`queue_key` keeps those of the built-in harness with the same `executable`.

## MCP servers

### Example

```toml
[mcp.exa]
url = "https://mcp.exa.ai/mcp"
headers_env = { "x-api-key" = "EXA_API_KEY" }

[roles.research]
mcp = ["exa"]
```

### The contract

An `[mcp.<name>]` table defines a server once, and `[roles.<name>] mcp` gives it to the agents of a role. piloop
writes it in the format of each harness, and passes API keys only as environment variables. A server is streamable
HTTP (`url`) or stdio (`command`). [MCP servers](/guides/mcp-servers) has the details.

## The evaluate command

### Example

```toml
evaluate = ["uv", "run", "python", "evaluate.py"]
evaluate_timeout = 600
```

```python
import subprocess

lines = subprocess.run(["python", "solve.py", "--check"], capture_output=True, text=True, check=True).stdout
print(f"METRIC score={lines.count('ok')}")
```

### The contract

The daemon runs the command in a clean worktree of each commit. It prints one line `METRIC <name>=<value>` for each
metric in `piloop.toml` and exits with 0 within `evaluate_timeout` seconds; otherwise the candidate is a `crash`. With
`PILOOP_UNITS_FILE` set, it can also write the result of each unit, for a paired bootstrap. See
[The evaluate command](/concepts/projects#the-evaluate-command).

```toml
[stop]

```

`[stop]` ends the campaign when one of its conditions holds; the daemon checks them on every tick, before it requests

## How piloop loads plugins

The **plugin host** is the part of piloop that finds, checks and loads plugins (`piloop.plugins.host`).

- **Entry points.** A plugin adds a provider with an entry point in the group of a capability, for example
  `piloop.runtimes`. The name of the entry point is the name of the provider. piloop's own providers are entry points
  of the `piloop` package, in the same groups, so piloop loads them as it loads a plugin's.
- **All or nothing.** piloop loads every provider of a capability and checks each one. Then it registers all of them,
  or none.
- **Before the daemon starts.** The daemon loads each capability that it uses before it opens the database. It does
  not start when an entry point does not import, names an object of the wrong type, or uses a name that another
  provider has. It also does not start when `config.toml` selects a provider that does not exist.
- **The same checks elsewhere.** `piloop serve --check`, `piloop doctor` and `piloop plugins` do the same checks.
  `piloop restart` and `piloop upgrade` do them first, and keep the daemon running if it would not start again.
  A broken storage backend that nothing selects is only a warning.
- **Selection.** Each capability says where the configuration selects its provider. The runtime and the storage
  backend have their own keys. A new capability uses a table in `piloop.toml`: `provider` is the name of the provider,
  and the other keys are its parameters. If no provider has that name, the error names the key and lists the names
  that exist.
- **Versions.** An entry point group is one version of a contract. An incompatible change to a contract gets a new
  group.
- **Two kinds of contract.** A provider of the runtimes, the storage backends, the triggers or the roles can get live
  objects of piloop: processes, files, a database session. A provider of a pure capability gets data only. piloop
  loads, selects, lists and unloads both kinds in the same way.

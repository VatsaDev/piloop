## Decisions

| Decision | Choice | Why |
|---|---|---|
| Plugin mechanism | In-process Python: package entry points, typed protocols, one shared host. | It fits the current daemon. |
| Plugin scope | Every capability mounts through one plugin host. First-party and third-party providers load, configure, inspect, and replace the same way. | A user adapts piloop to a use case through declared capabilities, without a fork. |
| Plugin tiers | Host plugins may receive live host capabilities. Pure plugins use a data-only contract that maps to WIT. | A pure plugin can later run out of process or as a Wasm component, with no new contract and no dependencies in piloop's environment. |
| Unit of replacement | A campaign type: one bundle of objective, selection, stop, and progress providers. | A research strategy is more than a verdict callback. |
| Campaign types | Base and optimization in core. Goal as a plugin later. | Not every campaign has a loss or a head. |
| Campaign structure | Flat rows, with at most one parent each. | A program can group sub-campaigns without nested state. |
| Measurement | F(evaluator, benchmark, artifact) = result. | piloop can compare benchmarks and evaluators, and keep old data readable when a format changes. |
| Naming | The evaluator is the runner plugin. The benchmark is what it runs. | Today's code calls the benchmark `evaluator`. The schema slice renames it. |
| Artifacts | Two plugin seams: the artifact kind and the storage backend. Any combination works. | A git tree is the first kind, not the only one. Anything can store bytes. |
| Mutations | Typed operations with receipts, plus a cursor-based event feed. `piloop sql` keeps its writes. | One mutation path for structured callers. SQL stays the simple interface for agents. |
| Composition | Resolved at boot. Changed by an orderly restart. No hot reload. | Hot reload needs lifecycle machinery that no use needs yet. |
| Failure | An unknown or missing provider, type, or evaluator fails before launch. | A silent fallback hides a wrong configuration. |

## Purpose

A user should be able to state the objective, constraints, and research strategy of a campaign, inspect the evidence,
and replace the strategy without changing piloop. Today an external program can call the CLI and query the database,
but a different strategy needs internal tables and daemon behavior.

The target is one shared composition and lifecycle model, typed domain capabilities, and public operations that work
for built-ins, plugins, people, agents, and external programs. Today's workflow becomes the optimization campaign type,
the default. It keeps one machine, one daemon, SQLite, and the existing artifact store. Remote execution is a separate
proposal that plugs into these seams.

**Success:** an external controller reads a consistent snapshot, follows committed changes, submits ideas, requests
attempts, and reacts to measurements, with no private imports or patches to the daemon. A restart of that controller
loses no accepted work and launches nothing twice. An installed plugin replaces a first-party provider through
configuration, and first-party code uses the same interface.

## Shared abstractions

| Abstraction | Contract |
|---|---|
| Capability | A public identifier, an interface version, a typed protocol, error semantics, and ownership rules. |
| Provider | An implementation of a capability. A singleton binding has one provider; a named registry says so in its contract. |
| Plugin definition | Identity and version, a validated configuration schema, the capabilities it needs and provides, and an entry point. |
| Plugin instance | A stable id, resolved configuration, selected dependencies, a lifecycle state, and attributed failures. |
| Composition | The instances, bindings, configuration sources, and dependency graph of a daemon or a campaign. |

Use package entry points for discovery, Pydantic for configuration, protocols for interfaces, and context managers for
ordered cleanup. Start with daemon and project scopes. The composition resolves before research starts. Cycles,
missing or ambiguous providers, and incompatible versions are errors. A failed activation unwinds what it acquired.
The default composition uses the same activation path as a replacement. Status shows the provider, version, and
configuration source of every binding.

Each accepted run records the composition revision and the execution provider. It stores secret references, never
secret values. If a provider is missing after a restart, the affected work holds with an actionable error. It never
resumes through another implementation.

## Plugin tiers

Every capability mounts through one plugin host: runtimes, storage backends, transports, planning, the experiment
workflow, measurement, selection, context, reporting, auth, and model access. First-party and third-party providers
load, configure, inspect, and replace the same way. A user customizes piloop through declared capabilities, never by
reaching into internals. Each slice of the migration exposes more of piloop as capabilities. Composition happens at
boot, with no hot reload.

The two tiers are both first-class plugins. They differ only in contract.

| Tier | Examples | Contract | Transports |
|---|---|---|---|
| Host plugins | Runtimes, storage backends, transports, auth, model access. | May receive live host capabilities. Not limited to the WIT types. | In-process Python now. Some can become Wasm later, such as a storage backend over WASI HTTP. |
| Pure plugins | Planners, selection, stop and objective policies, evaluators, artifact kinds. | Data in, data out, in WIT-mappable types. | In-process Python now. Out of process over JSON, and Wasm components, later. |

A pure-plugin interface uses only types that map to WIT: records of primitives, enums, lists, optionals, maps, and
typed result and error variants. No live object crosses the boundary: no database session, repository, daemon, or
global. A pure plugin imports no piloop internals. The host passes it every capability it uses, explicitly. A test
checks the allowed types on every pure-plugin interface.

One pure-plugin contract has three transports: in-process Python, out of process over JSON, and a Wasm component. Out
of process, a plugin runs in its own environment, so its dependencies never enter piloop's environment. Only the
in-process loader is built now.

## Capabilities

| Capability | Responsibility and current implementation |
|---|---|
| Research operations | Validated mutations, receipts, and authoritative events. `piloop/campaign/ops.py` is the start. |
| Queries and event reader | Consistent snapshots and cursor reads over committed facts. |
| Agent runtime | Start, observe, steer, stop, and reattach agents. The `Runtime` protocol and its adapters. |
| Campaign type | A bundle of objective, selection, stop, and progress providers. |
| Experiment workflow | Prepare an attempt, collect the artifact it makes, and reconcile interrupted work. Keyed by artifact kind; git worktrees are the provider for git trees. |
| Evaluator | Run a benchmark on an artifact and return a result, with failure and provenance, independently of a verdict. |
| Artifact kind | What an artifact is, how to hash it, and how to materialize it. |
| Storage backend | Where bytes live: `put`, `get`, `missing`, and `list` by content hash. The existing remotes are the first providers. |
| Experiment planning | The next idea, base, role, and harness, from eligible work and free resources. |
| Context policy | The lessons, history, documents, and instructions that an agent reads. The exact brief is kept. |
| Harness support | Launch definitions, usage readers, MCP renderers, and capture. |
| Model access | How an agent reaches a model: harness logins, a model gateway, or API keys. |
| Auth | Who a caller is and what it may do. The OS user locally. |
| Progress and reporting | What status, watch, and agents show of a campaign's type. |
| Triggers and roles | React to state and request agent work through operations. |

Protocols stay narrow. A provider does not import a database session, the daemon, or another provider's private types
to do its public job. "Everything is a plugin" does not mean every helper becomes a package, or that a plugin replaces
a harness's own model loop.

## Campaign types

A campaign, a project in today's CLI, has a type.

| Type | What it has | Where it lives |
|---|---|---|
| Base | No goal, no loss, and no agents of its own. People and agents file ideas, artifacts, notes, and tags through the operations. | Core. |
| Optimization | A loss, a head, a bar, keeps, tracks, and plateau and target stop rules. Today's behavior. | Core, and the default. |
| Goal | Completion, for example when every proof obligation is discharged. | A plugin, later. |

Head, bar, and keep semantics belong to the optimization type only. Reports and stop policies read the progress view
of the campaign's type. Campaigns stay flat, and a tree index sits on top: each campaign has at most one parent. For
example, a campaign to build a C compiler can have sub-campaigns for spec compliance, for optimization, and for a
verified executable. Each campaign keeps its own type, ideas, and evidence.

## Measurements and artifacts

A measurement is F(evaluator, benchmark, artifact) = result.

| Term | Meaning | Today |
|---|---|---|
| Evaluator | The runner, a plugin. It is experimental, stable, or deprecated. A deprecated evaluator stays loadable for old data. | One evaluator: it runs the benchmark as a process. |
| Benchmark | What the evaluator runs. Two benchmarks can be declared equivalent when a format changes. | The evaluate command, its metrics, and its linked files. The code calls this an `evaluator`. |
| Artifact | What is measured, by kind and content hash. | A candidate's git tree. |

Artifact kinds and storage backends are separate seams. A kind says what an artifact is and how to materialize it: a
git tree, a file, a theorem, a dataset. A backend says where its bytes live: local disk, S3, GCS, a content-addressed
store, a git remote. Any kind can use any backend.

Two uses need no campaign:

- **Secondary evaluation.** An operation measures a selection of artifacts under an evaluator and a benchmark. It
  changes no verdict, bar, or head. For example: measure the best artifacts again under benchmark B, or measure how
  well benchmark A correlates with benchmark B.
- **Artifact checks.** A check of a property of one artifact is an observation on that artifact.

Staged evaluation, a cheap benchmark first and an expensive one for the artifacts that pass, uses the
[evaluation queue](/concepts/verdict#the-evaluation-queue).

A benchmark can be controlled separately from the code that agents edit, and declare its code, input, and environment
identities. Search-time feedback and final held-out validation can be separate benchmarks.

## Operations, facts, and queries

| Contract | Meaning |
|---|---|
| Operation | A request to change state, with validated input and a receipt. Acceptance does not mean that the work is done. |
| Fact | An immutable record of a committed change, a row of `events`. Reading it runs nothing again. |
| Live hook | An extension point during an operation. Observers cannot affect correctness; a veto uses a declared decision interface. |
| Query | A read with a version and a cursor where consistency matters. |
| Artifact | Addressable evidence. Events carry references, not large bodies. |

The daemon, the CLI, plugins, and external transports call the same operation implementations. Operation names and
schemas are public; Python classes and tables are not. Plugins register namespaced operations, queries, and fact
schemas through the shared host. A reader keeps an envelope with an unfamiliar payload as opaque JSON, so installing a
plugin never strands another reader.

| Rule | Behavior |
|---|---|
| Commit | One transaction validates the request, checks the expected revision, writes the change and its facts, and stores the receipt. A response follows the commit. |
| Repeat | The same request id and content return the first receipt. The same id with other content is an error. Receipts live as long as their campaign. |
| Stale state | A decision based on an old revision is refused with the current revision. |
| One fact per change | Each fact has one producer. An operation writes no second event for a change that a trigger already logs. |
| Event reads | Bounded reads after a cursor, with a campaign and kind filter. A snapshot comes with its cursor. Delivery is at least once; a consumer checkpoints its own cursor. |
| External effects | An operation that launches work records its intent before the effect. A crash between the effect and its handle is reconciled, never blindly repeated. |
| Distinct failures | A missing provider, a failed measurement, a cancelled attempt, and an uncertain effect are distinct states. |

`piloop sql` keeps accepting writes, through its authorizer and the audit triggers. Typed operations serve people,
APIs, and control verbs. If SQL writes cause problems later, piloop can restrict them to operations then.

## The optimization campaign type

The optimization type reproduces today's behavior: ready ideas and dependencies, track shares, exploration from pinned
candidates, harness rotation, the research, watchdog, and scout roles, lessons, evaluation, confidence and guardrail
checks, head advancement, merges of concurrent keeps, and recovery. Other compositions of this type can choose other
policies, such as several candidates on a Pareto frontier or repeated measurement before selection.

A planning binding names one authority for its scope. An external planner replaces the default planner for that scope;
the two never compete. When the controller disconnects, accepted work continues and unplanned work waits. A fallback
is an explicit, recorded configuration change.

## Lessons from DeepSeek Harness

The design study uses DeepSeek Harness at
[`1517a4d`](https://github.com/deepseek-ai/deepseek-harness/tree/1517a4dbca0a2789ff1d41ba439600f8547d23fa)
(MIT) as an architectural reference. It is not a dependency, and no code is copied.

| Its mechanism | Use in piloop |
|---|---|
| Capability, provider, and consumers | Consumers depend on an interface; composition picks the implementation. |
| One lifecycle record per plugin instance | Dependencies, registrations, and errors are attributed to an instance. |
| Registrations as owned, reversible effects | A failed activation unwinds; shutdown closes dependents first. |
| Profiles and bundles | Campaign types and defaults assemble through the ordinary composition path. |
| Separate session records, hooks, and services | Facts, hooks, and operations have separate contracts. |

Its live events are process-local, not a durable replay protocol, and its lifecycle does not recover an external agent
process. piloop keeps explicit durable intent, handles, and reconciliation. In-process scopes route capabilities; they
do not sandbox trusted Python code.

## Migration

Each slice migrates one capability completely: the provider, every first-party consumer, recovery, tests, docs, and
the deletion of the old path. There is never a permanent "plugin mode" beside a special case.

| Slice | Change | Acceptance gate |
|---|---|---|
| 0. Schema | A campaign `type` column (default `optimization`) and a `parent` pointer. Rename the code's `evaluator` table, columns, and configuration to `benchmark`, with a configuration bridge. An `evaluator` column on measurements with one value. | Existing databases migrate: every campaign is `optimization` with no parent, and every measurement has today's evaluator. Behavior does not change. |
| 1. Operations and event feed | Machine I/O on the CLI (`--json`, request ids, receipts), event reads after a cursor, and stale-state checks. The control verbs in `piloop/campaign/ops.py` (`piloop pause`, `piloop resume`, `piloop candidate verdict`, `piloop measurement add`, and `piloop idea status`, `link`, `unlink`, `base` and `track`) move onto these operations, with project stop and run and agent cancel. | A separate controller snapshots, submits an idea, requests work in its planning scope, reads results, and reconnects without private imports. Every control verb returns a receipt. |
| 2. Shared host | Instances, dependency resolution, lifetimes, and composition inspection. Tenants: runtimes, storage backends, evaluators, and artifact kinds. | Contract tests pass for each tenant. Missing and duplicate providers fail before launch. Partial activation unwinds. The type test passes on every pure-plugin interface. The old runtime and store loaders are deleted. |
| 3. Planning | Idea, base, role, and model selection leave scheduler admission. The current planner and an external planner. | Ordering, dependencies, track shares, exploration, and capacity stay. A replacement disables default planning for its scope. A duplicate decision launches nothing twice. |
| 4. Context | Context selection mounts through its protocol. Storage and search stay. | The delivered brief stays equivalent. A replacement policy works. Briefs stay queryable. |
| 5. Measurement and selection | Separate measurement, objective, selection, and merge requests. The optimization type becomes the first type bundle. Add the base type and secondary evaluation. | Concurrent keeps, remeasurement, benchmark changes, interrupted scoring, and merge recovery still work. A base campaign has no head. A secondary evaluation moves no head. |
| 6. The rest | Roles, triggers, stop and progress, harness support, the experiment workflow by artifact kind. | Every capability is inspectable and replaceable through the host. The remaining special-case paths are deleted. |

Slices 0 and 1 are in progress and do not depend on each other. Slice 1 comes before the shared host because external
controllers and remote execution depend on operations. Existing databases keep their ids, commits, measurements,
lessons, artifacts, and events. Existing entry-point groups stay as inputs to the one shared loader.

Keep the existing tests for interrupted work, daemon handoff, restarts during evaluation, concurrent head movement,
resumed merges, benchmark changes, and track allocation. Add contract tests per capability, and end-to-end tests with
a separate controller process, a real git repository, and fault injection: a commit before its response, an effect
before its handle, repeated requests, stale revisions, and reconnects.

## Ownership and retirement

| Addition | Owner | Deleted when |
|---|---|---|
| The shared host | plugin-host maintainer | An abstraction in it serves neither the default composition nor a supported replacement. No unused hooks. |
| Extraction scaffolding | each slice's author | In that slice, when all its consumers use the capability. |
| Configuration bridges | configuration maintainer | After the documented deprecation period. |
| An external transport adapter | integration maintainer | No supported client uses it. It never owns a mutation. |
| `type`, `parent`, and `evaluator` columns | schema maintainer | Never: they are data. A plugin type lives in its plugin's package. |
| An experimental evaluator | its author | It is not stable two minor releases after it ships. A deprecated one stays loadable while a measurement names it. |
| Example replacement providers | the capability's author | They demonstrate no supported extension. |

Receipts and evidence are data, not a cache. They are deleted only with their campaign.

## Open in implementation

The first implementation PR of each slice settles these with executable contracts:

1. The Python activation interface, the composition schema, and the version rules.
2. The operation, query, and event schemas, and the granularity of revisions.
3. Provider identity, and the rule for recovering work across a package upgrade.
4. The smallest progress view that a second selection strategy needs.

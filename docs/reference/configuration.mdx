`piloop.toml` is at the root of the campaign repo. `piloop init` reads it again each time you run it, and stores a
copy. The daemon uses that copy, so an edit takes effect only when you run `piloop init`.

To override a key when `piloop init` reads the file, set `PILOOP_CAMPAIGN_<KEY>`. Join nested keys with `__`, for
example `PILOOP_CAMPAIGN_RUNTIME=herdr` or `PILOOP_CAMPAIGN_ROLES__IMPLEMENTER__MAX_CONCURRENT=2`. The stored copy keeps the
override until the next `piloop init`. The variable has no effect on `piloop serve`.

A type in the tables links to the section that describes it. A table that you leave out has the defaults of its
section.

## Metric

One metric. The evaluate command prints it as a `METRIC name=value` line.

| Key | Type | Default | Description |
|---|---|---|---|
| `name` | string | required | The name of the metric, as the evaluate command prints it. |
| `direction` | `higher` \| `lower` | required | `higher` when a larger value is better, `lower` when a smaller value is better. |
| `role` | `primary` \| `guardrail` \| `watch` | `"watch"` | How the metric affects the verdict. A `primary` metric must beat the bar with confidence for a `keep`, and each track has exactly one. A `guardrail` may get worse by at most its `margin`, or the candidate is at most `interesting`. It must never pass its `floor`, or the candidate is a `discard`. A `watch` metric is recorded and never affects the verdict. |
| `track` | string \| null | `null` | Primary metrics only. The name of the track (objective) that this metric is the primary of. When unset, the track has the metric's name, so a campaign with one primary needs nothing here. With several primaries, each one names its own track, and each track needs a `[tracks.<name>]` table. |
| `margin` | number \| null | `null` | The largest regression from the bar that a candidate may show, in the metric's own units (an absolute value, not a fraction). Required on a guardrail. Also required on every primary of a campaign with several tracks: when a candidate of another track is judged, that primary is a guardrail. When the evaluate command writes per-unit results, the margin is tested on the confidence bound of the bootstrap. Otherwise it is tested on the aggregate. |
| `floor` | number \| null | `null` | Optional. The worst value a candidate may have: at least this value for `higher`, at most this value for `lower`. ## TrackConfig

`[tracks.<name>]`: one track of the campaign. A track is an objective with its own primary metric and brief.

A track has the name of its primary's `track`, or else the name of the primary. All tracks build on one trunk. A
run starts from the head, which is the latest keep on the trunk. A keep on any track must also hold the primary of
every other track within that primary's `margin` and `floor`. A campaign with one primary has one track and
needs no table. A campaign with several primaries needs one table for each track, and the shares must sum to 1.

Experimental: campaigns with more than one track.

| Key | Type | Default | Description |
|---|---|---|---|
| `share` | number | `1` | The fraction of the `max_concurrent` of each role that does runs that the ideas of this track get. A free slot of a role goes to the track that is furthest below its share and has an idea that can run, and then to the most urgent idea of that track. A track with no idea that can run gives its slot to another track. A share of 0 stops the track: its ideas wait. |
| `addendum` | string \| null | `null` | A repo-relative file that is appended to the brief of this track's runs, after `[roles.implementer] addendum`. Use it to say how work on this objective is done, for example "profile first" or "keep the output identical". |

## Harness

`[harness.<name>]`: how to launch one coding agent.

piloop substitutes these placeholders in both argument lists: `{model}`, `{effort}` (the role's `effort`),
`{session_id}`, `{cwd}` (the agent's working directory), `{log_dir}` (the directory of the agent's brief and
logs) and `{prompt}` (the first prompt, which names the file that holds the brief). An element that is exactly `{mcp}` expands to the role's MCP
servers, in the form that `mcp` names. The built-in harnesses run without permission prompts: agents run
in worktrees that the daemon owns and throws away, and a sandbox that cannot reach the repo's `.git` cannot
commit. The built-in Claude harness passes `--settings` that move a foreground Bash command to the background
after 5 minutes.

When the argument list in use contains `{session_id}`, piloop creates the session id. Otherwise the runtime
reports it, or reads it with `session_id_pattern`.
When the agent ends, `entire session attach` takes this id, and `usage` uses it to find the session file and
read the tokens the agent spent.

## QueueKey

`queue_key`: the key that queues a typed message for the end of the agent's turn.

The message is typed into the composer, then the key is pressed. A harness that reads a burst of input as a paste
swallows a key that arrives inside the burst, so the key waits until the text is drawn, and is pressed again while
`pending` is still at the bottom of the screen, which shows that the agent did not take it yet.

| Key | Type | Default | Description |
|---|---|---|---|
| `key` | string | required | The key, as `herdr agent send-keys` names it, for example `tab`. |
| `pending` | string | required | Text at the bottom of the screen while the composer still holds the typed message. |

## ScoutRole

`[roles.scout]`: the scout files outside techniques as seeds for the measured losses. It is off by default.

Every `interval` seconds, a scout sweep states the open problems of the campaign from the evidence, and searches
X, GitHub and arXiv for outside techniques that address them. It files at most `seeds` of them as seeds, signed
`scout#<agent session id>`, and puts the rest in the technique library (the `techniques` table). It never files a
defined idea. The search tool limits what one sweep spends on xAI (`scripts/xai_search_mcp.py --max-usd`).

Experimental: the scout.

| `command` | list\[string\] \| null | `null` | The command (argv) of a stdio server, for example `["python3", "/path/to/server.py"]`. |
| `env` | list\[string\] | `[]` | stdio only. The environment variables that the server reads, for example `["XAI_API_KEY"]`. |

## Stop

`[stop]`: conditions that end the campaign. One is enough. Without the table, the campaign has no end.

The daemon checks the conditions on every tick, before it requests anything. When one holds, the campaign is
`stopped` (`campaigns.status`, `stopped_reason`). Running implementers are told to commit and stop, and are ended
10 minutes later. What they committed is scored. An implementer in the middle of a turn reads the message only when the
turn ends: one that is ended before it left its finding ends its run `campaign_stopped`, which does not
count toward `max_runs` or `plateau`. Pending requests and queued runs are dropped
(`campaign_stopped`). The `stopped` triggers fire once, which by default requests the watchdog's closing
review, and the triggers request nothing more. The daemon files no seeds for the campaign either. An agent that you
request with `piloop launch` after the stop still starts.

`piloop campaign stop` stops a campaign the same way on the next tick, whatever this table says. With `--kill`,
the implementers are ended at once instead of told. `piloop init` resumes a stopped campaign when this table changed.

`max_runs` and `plateau` count the same runs: those that reached the evaluator, with a candidate that is
measured or waits for its measurement. A run that ended at a cheap check with no commit, with only
`Piloop-Eval: skip` commits, or before it committed because of a harness or host fault, says nothing about the
metric, so it counts toward neither. A run that a daemon stop, a daemon crash or a campaign stop ended does not
count either. `[spend]`, `max_tokens` and `max_hours` stay hard limits on what all runs cost.

| Key | Type | Default | Description |
|---|---|---|---|
| `target` | number \| null | `null` | Stop when the primary metric at the head (the latest keep on the trunk) reaches this value, in its direction. Only for a campaign with one track. |
| `max_runs` | integer \| null | `null` | Stop after this many runs that count (see above), once none is queued, running or being scored. A run also counts while it is queued, running or being scored, so piloop never starts more runs than this. A finished run that does not count frees its place, and piloop starts another run in it. |
| `max_hours` | number \| null | `null` | Stop after this many hours of wall-clock time since the first run of the campaign started. The time that the campaign was paused (`piloop pause`) does not count. |
| `max_tokens` | integer \| null | `null` | Stop when all the agents of the campaign together spent this many tokens (the `total` of `agent_sessions.usage`), summed over the agents that ended. |
| `plateau` | integer \| null | `null` | Stop after this many finished runs that count (see above) without a new `keep` candidate. The count starts again at each keep, and when the campaign is set `active` after a stop (`piloop init`, or an UPDATE of `campaigns.status`), so a reactivated campaign gets this many runs again. A new evaluator alone does not reset it. |

## Spend

`[spend]`: a hard budget in USD on what the campaign costs outside piloop, for example GPUs or APIs.

Every `interval` seconds, the daemon runs `command` to read the spend from the campaign (`campaigns.spend_usd`,
`spend_error`, `spend_at`). When the spend passes a `notices` threshold, the daemon posts one note to the
inbox at priority 1. At `limit`, the daemon posts one escalation at priority 0, and the stop rule holds the
campaign: the daemon launches no agent and starts no evaluation (no request, no re-measure). Work that already
runs finishes and is scored. A command that fails holds the campaign in the same way, with one escalation for each
series of failures: an unknown spend is never read as $0. To resume, raise `limit` and run `piloop init`. The
built-in stop rule `limits` holds; a stop rule of a plugin must read the spend, or `piloop.toml` is refused.

| Key | Type | Default | Description |
|---|---|---|---|
| `command` | list\[string\] | required | The command (argv) that prints the campaign's spend so far in USD, as one number. It runs at the repo root with the daemon's environment, which is where its secrets come from. It must exit with code 0 within one minute. Example: `["uv", "run", "scripts/spend.py"]`. |
| `limit` | number | required | The spend in USD at which launches and evaluations hold. |
| `notices` | list\[number\] | `[]` | Amounts in USD below `limit`. When the spend passes one, the daemon posts one note to the inbox. |
| `interval` | number | `300` | The number of seconds between two runs of `command`. |
| `closing_review` | `run` \| `skip` \| `wait` | `"run"` | What happens to the closing review when the campaign stops while launches are held (`piloop campaign stop`): `run` it anyway, `skip` it, or `wait` until the hold ends. |

Never name a document that is derived from validation or test data. |
| `wake_budget` | integer | `400` | The size in tokens (about 4 characters each) of the overview that opens the briefs of implementers and research sweeps: the current lesson of each mechanism family on the same repo, from the newest campaign that tried it, one line each. The brief then says how to read more. A role can change it with `[roles.<kind>] wake_budget`. 0 turns it off. |

## LowWaterTrigger

The backlog of runnable ideas is shorter than its target, and there is a reason to sweep now.

The target is one idea per run slot plus `buffer`. So ideas exist before slots free up, and a free slot does not
wait a whole sweep for an idea. The ideas that the role's sweeps in flight can insert already count as backlog.
Nothing is requested while every slot of the role is busy. Runnable ideas count. Ideas blocked only by
prerequisites in flight also count, because they run when those finish. An idea blocked by a prerequisite that is
not running does not count. Below the target, a sweep fires for one of these reasons:

- The campaign has no sweep yet, so there is nothing to wait for.
- The last batch was killed. Lost prompts, timeouts or a daemon stop say nothing about the backlog, so the batch
  is retried once. This applies to a streak of killed rows no longer than one batch (`max_concurrent`). A second
  killed batch is a systemic fault and counts as a normal last sweep.
- New results: runs finished since the role's latest row started, which that sweep could not read. A sweep with
  nothing new to read reads the same history and proposes nothing. So each consecutive sweep that defined no idea
  doubles the number of finished runs the next sweep waits for. A sweep that defines an idea resets this. The
  wait is never longer than what can still come: with no run in flight, the finished runs are all there is.
- The backlog is low. The role keeps sweeping while the backlog is short, not only when results come in or a slot
  is idle. A sweep that defined an idea is followed at once. After empty sweeps, the role rests 2**n − 1 times as
  long as its latest ended sweep took. n is the number of consecutive ended sweeps, killed ones included, that
  defined no idea. An empty queue never deadlocks, and a role that keeps finding nothing uses at most 1/2**n of
  the wall-clock time.

It requests enough sweeps to fill the shortfall at the role's `max_ideas` each, within the role's free slots.
Nothing is requested while the queue holds runnable ideas for the head to be measured again (`Backlog.on_hold`):
no idea that a sweep adds could run sooner.

| Key | Type | Default | Description |
|---|---|---|---|
| `kind` | string | `"low_water"` |  |
| `buffer` | integer | `2` | The number of ready ideas to keep in addition to one for each run slot (the `max_concurrent` of every role that does runs). With this backlog, a free slot finds an idea at once and does not wait for a sweep. A larger value makes implementers wait less for the role, but the ideas they run are older. |

## SeedTrigger

A seed was filed after the role's latest agent started, and a slot of the role is free.

It fires however full the backlog is. If the latest row got the seed but was killed, the seed is retried, once per
batch, as `low_water` retries. A seed that a sweep read and did not develop is in the next sweep's brief,
whatever trigger fires it. Gotcha: a sweep's brief is read a moment before its row's `started_at` is set, so a
seed filed in that moment waits for the next sweep.

| Key | Type | Default | Description |
|---|---|---|---|
| `kind` | string | `"seed"` |  |

| Key | Type | Default | Description |

## StalledTrigger

The campaign reached a new stall step, and no sweep of the role started in it, however full the backlog is.

The campaign has stalled when the runs since the last keep reach the stall mark (`piloop.campaign.stop.stall`).
Each further mark of runs without a keep is a new step, and a keep ends the stall. The backlog may hold no idea
that pivots, and the brief of a sweep on a stall allows one idea of the role's own. So a stall of N runs gets
about N / mark sweeps, not one per result. The back-off of `low_water` for new results still applies, and a
killed sweep is retried at the next step. As with `low_water`, nothing is requested while every slot of the role
is busy, while its `max_ideas` is 0, or while the queue holds its ideas for the head (`Backlog.on_hold`).

| Key | Type | Default | Description |
|---|---|---|---|
| `kind` | string | `"stalled"` |  |

## Global settings: `config.toml`

`$PILOOP_HOME/config.toml` holds the settings that every campaign of one `PILOOP_HOME` shares. To override a key, set `PILOOP_<TABLE>__<KEY>`, for example `PILOOP_STORAGE__MIN_FREE_GB`.

### `[storage]`

`[storage]`: the artifact store every campaign of this PILOOP_HOME archives its workspace into.

The keys here hold for every backend. Blobs live in `<PILOOP_HOME>/store`, and in the remote too when
`[storage.backend]` is set. The artifact store page of the docs describes the modes.

| Key | Type | Default | Description |
|---|---|---|---|
| `evict_after_days` | number \| null | `null` | Drop the local copy of a blob the remote holds once it is this old (since it was stored or fetched); 0 drops it as soon as it is uploaded, so the local directory is only a staging area and every read fetches. Unset: by age never. |
| `local_max_gb` | number \| null | `null` | Drop the local copies of the oldest blobs the remote holds until the local store is at most this size. |
| `min_free_gb` | number | `20` | Free space, in GB, that archiving keeps on the disk of the local store. Storing a file writes its compressed copy first, so the daemon removes the workspace copies of archived files, oldest archive first, while the disk has less than this free, and it archives in batches that fit above it. |

`[storage.backend]` picks the backend that mirrors the store by its `kind`, and the backend owns the other keys of the table. The keys of `[storage]` stay the same whatever the backend. The same store, mirrored to S3 or to Google Cloud Storage:

<CodeGroup>

```toml S3
[storage]
evict_after_days = 30
min_free_gb = 50

[storage.backend]
kind = "s3"
url = "s3://my-bucket/piloop"
storage_class = "GLACIER_IR"
```

```toml GCS
[storage]
evict_after_days = 30
min_free_gb = 50

[storage.backend]
kind = "gcs"
bucket = "my-bucket"
prefix = "piloop"
storage_class = "COLDLINE"
credentials_file = "/etc/piloop/gcs-key.json"
```

</CodeGroup>

A package adds a backend with an entry point in the `piloop.stores` group: see [storage backends](/architecture/extension-points#storage-backends). The built-in ones:

### `[storage.backend]` with `kind = "gcs"`

| Key | Type | Default | Description |
|---|---|---|---|

## Deprecated keys

These keys still work. Each one shows a `PiloopDeprecationWarning` that names the file, the key, its replacement and the release that removes it. The changelog lists them too.

- `[roles.worker]` is `[roles.implementer]`: the role that runs one idea in its own worktree. A key that `[roles.implementer]` sets too keeps its value there.
- `[roles.research.scout]` is `[roles.scout]`, a role of its own. The keys of `[roles.research]` that the scout used (`runtime`, `harnesses`, `model`, `timeout`, `mcp`, `addendum` and `workdir`) are copied into it, unless `[roles.scout]` sets them.
- The `scout` trigger of `[roles.research] triggers` is gone: the scout is a role with its own `cron`.
- `[roles.research] buffer` is the `buffer` of research's `low_water` trigger. Without `triggers` in the table, research gets its default triggers with that `buffer`.
- `[roles.research] context` is the top-level `context`: every sweep's research pack lists the files.
- `{claude_config_dir}` and `{codex_home}` in `[harness.<name>.usage] file` are `{env:…}` placeholders. `{claude_config_dir}` is `{env:CLAUDE_CONFIG_DIR:~/.claude}`, and `{codex_home}` is `{env:CODEX_HOME:~/.codex}`.
- In `config.toml`, `herdr_<key> = …` is `<key> = …` in its `[runtimes.herdr]` table. The Herdr settings are the Herdr runtime's own. Their environment variables (`PILOOP_HERDR_<KEY>`) do not change.
- In `config.toml`, `[storage.remote]` is `[storage.backend]`: the storage backend that mirrors the store. A key that `[storage.backend]` sets too keeps its value there.
- In `config.toml`, `max_evaluations` is `evaluations` in `[plugins.executor.pools.serve]`. A value that `[plugins.executor.pools.serve]` sets too wins.

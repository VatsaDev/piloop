`piloop.toml` is at the root of the campaign repo. `piloop init` reads it again each time you run it, and stores a
copy. The daemon uses that copy, so an edit takes effect only when you run `piloop init`.

To override a key when `piloop init` reads the file, set `PILOOP_CAMPAIGN_<KEY>`. Join nested keys with `__`, for
example `PILOOP_CAMPAIGN_RUNTIME=subprocess` or `PILOOP_CAMPAIGN_ROLES__IMPLEMENTER__MAX_CONCURRENT=2`. The stored copy keeps the
override until the next `piloop init`. The variable has no effect on `piloop serve`.

A type in the tables links to the section that describes it. A table that you leave out has the defaults of its
section.

## Tolerance

How far a metric may go: never past `floor`, nor worse than the bar by more than `margin` or `fraction`.

A guardrail has one, and so has each stop of a rung of the ladder. A guardrail tests its regression on the confidence bound of the bootstrap when the evaluate command reports
per-unit results or pairs, else on the aggregate. A stop of the ladder tests the rung's values.

| Key | Type | Default | Description |
|---|---|---|---|
| `floor` | number \| null | `null` | Optional. The worst value allowed, whatever the bar: at least this for `higher`, at most this for `lower`. |
| `margin` | number \| null | `null` | The largest regression from the bar, in the metric's own units: `20` for 20 ms. Not with `fraction`. |
| `fraction` | number \| null | `null` | The largest regression from the bar, as a fraction of the bar's value: `0.1` for 10%. Not with `margin`. |

## Metric

One metric that the evaluate command reports, by its name in `metrics` of its result.

Its `floor`, `margin` and `fraction` (`Tolerance`) apply to a guardrail, which needs a `margin` or a
`fraction`, and to each primary of a campaign with several tracks: when a candidate of another track is judged,
that primary is a guardrail.

| Key | Type | Default | Description |
|---|---|---|---|
| `name` | string | required | The name of the metric, as the evaluate command reports it. |
| `direction` | `higher` \| `lower` | required | `higher` when a larger value is better, `lower` when a smaller value is better. |
| `role` | `primary` \| `guardrail` \| `watch` | `"watch"` | How the metric affects the verdict. A `primary` metric must beat the bar with confidence for a `keep`, and each track has exactly one. A `guardrail` may get worse by at most its `margin` or `fraction`, or the candidate is at most `interesting`. It must never pass its `floor`, or the candidate is a `discard`. A `watch` metric is recorded and never affects the verdict. |
| `track` | string \| null | `null` | Primary metrics only. The name of the track (objective) that this metric is the primary of. When unset, the track has the metric's name, so a campaign with one primary needs nothing here. With several primaries, each one names its own track, and each track needs a `[tracks.<name>]` table. |
| `repeats` | integer \| null | `null` | Optional. Marks a noisy metric, such as a time: each evaluation of a run's candidate that this metric judges runs the evaluate command `repeats` times on the candidate and as many times on its bar, one after the other, and the verdict compares these pairs. Load then slows both sides alike. With several, the largest number counts. Allowed on a guardrail, and on a primary. |

## TrackConfig

`[tracks.<name>]`: one track of the campaign. A track is an objective with its own primary metric and brief.

A track has the name of its primary's `track`, or else the name of the primary. All tracks build on one trunk. A
run starts from the head, which is the latest keep on the trunk. A keep on any track must also hold the primary of
every other track within that primary's `margin` and `floor`. A campaign with one primary has one track and
needs no table. A campaign with several primaries needs one table for each track, and the shares must sum to 1.

Experimental: campaigns with more than one track.

| Key | Type | Default | Description |
|---|---|---|---|
| `share` | number | `1` | The fraction of the `max_concurrent` of each role that does runs that the ideas of this track get. A free slot of a role goes to the track that is furthest below its share and has an idea that can run, and then to the most urgent idea of that track. A track with no idea that can run gives its slot to another track. A share of 0 stops the track: its ideas wait. |
| `addendum` | string \| null | `null` | A repo-relative file that is appended to the brief of this track's runs, after `[roles.implementer] addendum`. Use it to say how work on this objective is done, for example "profile first" or "keep the output identical". |

## Harness

`[harness.<name>]`: how to launch one coding agent.

piloop substitutes these placeholders in the argument lists: `{model}`, `{effort}` (the role's `effort`),
`{session_id}`, `{cwd}` (the agent's working directory), `{log_dir}` (the directory of the agent's brief and
logs) and `{prompt}` (the first prompt, which names the file that holds the brief). An element that is exactly
`{mcp}` expands to the role's MCP servers, in the harness's own flags. The built-in harnesses run without
permission prompts: agents run in worktrees that the daemon owns and throws away, and a sandbox that cannot reach
the repo's `.git` cannot commit.

When `headless` contains `{session_id}`, piloop creates the session id. Otherwise the runtime reads it with
`session_id_pattern`. When the agent ends, the harness finds its session file by this id and reads the tokens
the agent spent. Without either, no tokens are recorded.

| Key | Type | Default | Description |
|---|---|---|---|
| `executable` | string | required | The program to run. |
| `headless` | list\[string\] | required | The arguments for a run without a terminal. Must include `{prompt}`. |
| `resume` | list\[string\] | `[]` | The arguments that continue the session of a run with a new prompt. When the agent's turn ends with messages queued for it (comments, `piloop prompt`), the runtime runs the harness again with these, `{prompt}` being the messages and `{session_id}` the session's id. Must include both. When empty, the agent takes no message while it runs. |
| `session_id_pattern` | string \| null | `null` | A regex with one group that finds the session id in the first lines of the process's stdout. Use it in a harness that cannot take its id as an argument (`{session_id}`). For example, Codex `exec --json` prints `{"type":"thread.started","thread_id":"<uuid>"}` first. |
| `home` | string \| null | `null` | The directory where the agent keeps its config and sessions: a path, which may start with `~` or name a variable as `{env:NAME:default}`. A harness that reads usage finds its session files under it, and the daemon's service unit carries `NAME`. |
| `session_env` | list\[string\] | `[]` | The variables the agent sets for the processes of its session. piloop clears them for every agent, so an agent started from inside such a session is not its child. |
| `env` | dict\[string, string \| [SecretRef](#secretref)\] | `{}` | Variables of the agent's environment: a value, or a secret, `{ secret = "NAME" }`. For example a model gateway, `{ ANTHROPIC_BASE_URL = "https://gw.example.com", ANTHROPIC_API_KEY = { secret = "ANTHROPIC_API_KEY" } }`. When unset, the agent uses the login of the machine that runs it. |

## Rung

`[[ladder]]`: one rung of the evaluation ladder, which a run's evaluation climbs before the full panel.

A rung without `evaluate` is reported by the evaluate command itself, as a line with `"rung": "<name>"` before
its full result. A rung with `evaluate` runs that command first, which reports one line. After each rung, the
climb of a run's own version stops when `stop` says so, and piloop ends the evaluate command.

| Key | Type | Default | Description |
|---|---|---|---|
| `name` | string | required | The rung's name, which its line names and which the measurements of it record. |
| `stop` | dict\[string, [Tolerance](#tolerance)\] | required | When the climb stops at this rung, by metric of `[[metrics]]`. Example: `{ accuracy = { margin = 0.03 }, latency_ms = { fraction = 0.1 } }`. |
| `evaluate` | list\[string\] \| null | `null` | Optional. A command (argv) of its own, which runs before the evaluate command and reports this rung alone. The rungs that have one come first in `[[ladder]]`. |

## ScoutRole

`[roles.scout]`: the scout files outside techniques as seeds for the measured losses. It is off by default.

Every `interval` seconds, a scout sweep states the open problems of the campaign from the evidence, and searches
X, GitHub and arXiv for outside techniques that address them. It files at most `seeds` of them as seeds, signed
`scout#<agent session id>`, and puts the rest in the technique library (the `techniques` table). It never files a
defined idea. The search tool limits what one sweep spends on xAI (`scripts/xai_search_mcp.py --max-usd`).

Experimental: the scout.

## LowWaterTrigger

The backlog of runnable ideas is shorter than its target, and there is a reason to sweep now.

The target is one idea per run slot plus `buffer`. So ideas exist before slots free up, and a free slot does not
wait a whole sweep for an idea. The ideas that the role's sweeps in flight can insert already count as backlog.
Nothing is requested while every slot of the role is busy. Runnable ideas count. Ideas blocked only by
prerequisites in flight also count, because they run when those finish. An idea blocked by a prerequisite that is
not running does not count. Below the target, a sweep fires for one of these reasons:

- The campaign has no sweep yet, so there is nothing to wait for.
- The last batch was killed. Lost prompts, timeouts or a daemon stop say nothing about the backlog, so the batch
  is retried once. A sweep that someone cancelled is not retried: after it, only new results start the next one. This applies to a streak of killed rows no longer than one batch (`max_concurrent`). A second
  killed batch is a systemic fault and counts as a normal last sweep.
- New results: runs finished since the role's latest row started, which that sweep could not read. A sweep with
  nothing new to read reads the same history and proposes nothing. So each consecutive sweep that defined no idea
  doubles the number of finished runs the next sweep waits for. A sweep that defines an idea resets this. The
  wait is never longer than what can still come: with no run in flight, the finished runs are all there is.
- The backlog is low. The role keeps sweeping while the backlog is short, not only when results come in or a slot
  is idle. A sweep that defined an idea is followed at once. After empty sweeps, the role rests 2**n − 1 times as
  long as its latest ended sweep took. n is the number of consecutive ended sweeps, killed ones included, that
  defined no idea. An empty queue never deadlocks, and a role that keeps finding nothing uses at most 1/2**n of
  the wall-clock time.

It requests enough sweeps to fill the shortfall at the role's `max_ideas` each, within the role's free slots.
Nothing is requested while the queue holds runnable ideas for the head to be measured again (`Backlog.on_hold`):
no idea that a sweep adds could run sooner.

| Key | Type | Default | Description |
|---|---|---|---|
| `buffer` | integer | `2` | The number of ready ideas to keep in addition to one for each run slot (the `max_concurrent` of every role that does runs). With this backlog, a free slot finds an idea at once and does not wait for a sweep. A larger value makes implementers wait less for the role, but the ideas they run are older. |

## NewsTrigger

New inbox items for the role's party, seeds, anomalies, verdicts and the stop: `piloop inbox wait`'s news.

Messages, escalations and the stop wake the role `quiet_seconds` after the first news, also while the campaign is
paused, held or stopped. The rest wakes it at most once in `routine_every`, and only while the campaign runs.
An agent of the role that is open already gets the news at once, in a note.

| Key | Type | Default | Description |
|---|---|---|---|
| `quiet_seconds` | number | `30` | How long the role waits after the first news to launch an agent, so that one agent takes a burst of it. |
| `routine_every` | number | `900` | The fewest seconds between two agents that only routine news wakes: verdicts, seeds and anomalies. |

## SeedTrigger

A seed was filed after the role's latest agent started, and a slot of the role is free.

It fires however full the backlog is. If the latest row got the seed but was killed, the seed is retried, once per
batch, as `low_water` retries, unless someone cancelled that row. A seed that a sweep read and did not develop is in the next sweep's brief,
whatever trigger fires it. Gotcha: a sweep's brief is read a moment before its row's `started_at` is set, so a
seed filed in that moment waits for the next sweep.

| Key | Type | Default | Description |
|---|---|---|---|

## SqlTrigger

A query on the piloop database returns at least one row.

The query may use two parameters: `:campaign`, the campaign's id, and `:since`, when the role's latest row
started (or when the campaign was registered), as UTC text (`2026-01-31 12:00:00.000000`). Compare `:since` with
a `created_at` column to fire only on what is new. The query is checked when `piloop.toml` loads: it must be
one statement that only reads.

| Key | Type | Default | Description |
|---|---|---|---|
| `when` | string | required | The query, for example `SELECT 1 FROM candidates WHERE campaign_id = :campaign AND verdict = 'keep' AND created_at > :since`. |

## StalledTrigger

The campaign reached a new stall step, and no sweep of the role started in it, however full the backlog is.

The campaign has stalled when the runs since the last keep reach the stall mark, `every`. Each further mark of
runs without a keep is a new step, and a keep ends the stall. The backlog may hold no idea that pivots, and the
brief of a sweep on a stall allows one idea of the role's own. So a stall of N runs gets about N / mark sweeps, not
one per result. The back-off of `low_water` for new results still applies, and a killed sweep is retried at the
next step. As with `low_water`, nothing is requested while every slot of the role is busy, while its
`max_ideas` is 0, or while the queue holds its ideas for the head (`Backlog.on_hold`).

| Key | Type | Default | Description |
|---|---|---|---|
| `every` | integer \| null | `null` | The runs without a keep that mark a stall. When unset, two rounds of the run slots: twice the sum of the `max_concurrent` of the roles that do runs. |

## StoppedTrigger

The campaign stopped. It fires once, when the runs that the stop wound down are judged.

The stop came from its stop rule or a request. So the closing review sees the final head. The watchdog's closing review is this trigger. The reason is ``campaign
stopped: <the condition>``.

| Key | Type | Default | Description |
|---|---|---|---|

## Global settings: `config.toml`

`$PILOOP_HOME/config.toml` holds the settings that every campaign of one `PILOOP_HOME` shares. To override a key, set `PILOOP_<TABLE>__<KEY>`, for example `PILOOP_STORAGE__MIN_FREE_GB`.

### `[storage]`

`[storage]`: how archiving uses the disk of this PILOOP_HOME. Where the blobs go is `[plugins.cas]`.

| Key | Type | Default | Description |
|---|---|---|---|
| `min_free_gb` | number | `20` | Free space, in GB, that archiving keeps on the disk of PILOOP_HOME. A worker removes the copies of linked inputs that no job uses after each job, under the same rule. |

## Deprecated keys

These keys still work. Each one shows a `PiloopDeprecationWarning` that names the file, the key, its replacement and the release that removes it. The changelog lists them too.

- `kind` in an entry of `[roles.<name>] triggers` is `provider`: `{ provider = "cron" }`.
- `[stop] <key>` is `[plugins.stop_rule] <key>`, a limit of the stop rule. A rule without that key refuses it. A key that `[plugins.stop_rule]` sets too keeps its value there.
- `[spend] limit` is `[plugins.stop_rule] hold_at = { spend = <value> }`. A value that it sets too wins.
- `[spend]` is a `command` source of `[[facts]]` that reads `spend`, after `campaign` and `optimization`. Its command prints one number, so it runs in `SPEND_COMMAND`. `notices` are those of `spend`, and `closing_review` is `while_held` of `[plugins.stop_rule]`. A `[[facts]]` that the file lists keeps its sources, and the spend's comes after them.
- The top-level `confidence` is `[plugins.verdict_rule] confidence`. A value that the table sets too wins.
- `PILOOP_CAMPAIGN_STOP__<KEY>` and `PILOOP_CAMPAIGN_CONFIDENCE` set keys of the rules' tables. They are `PILOOP_CAMPAIGN_PLUGINS__STOP_RULE__<KEY>` and `PILOOP_CAMPAIGN_PLUGINS__VERDICT_RULE__CONFIDENCE`. The old variable still wins over the file.
- The `anomaly` trigger is two triggers: `run_failed` and `dead_at_startup`, in its place in the list.
- `[plugins.stop_rule] max_spend` is `hold_at = { spend = <value> }`. A value that `hold_at` sets too wins.
- `[memory] wake_budget` and `[roles.<name>] wake_budget` are the `budget` of the role's `lessons` section. A role's own value wins over `[memory]`'s. A budget that differs from the role's old default sets the role's `sections` to its defaults with the lessons at that budget, or without them at 0. A role that sets `sections` keeps them. The watchdog's old default was 0: it now reads the lessons too.
- `[memory] documents` is `documents` in `[plugins.memory]`, of the `local` provider. A value that `[plugins.memory]` sets too wins.
- `mcp` and `[harness.<name>.usage]` are the harness's provider: it renders the servers and reads the usage. A table named after a built-in harness drops them: the provider's own come from `home`. A table with a new name gets `provider`: its usage's `tally`, else its `mcp`. A table that sets neither runs its argv and does nothing else, as before.
- In `config.toml`, `[storage.backend]` is the `remote` of `[plugins.cas] provider = "cached"`. Its `kind` is the remote's `provider`. `evict_after_days` and `local_max_gb` of `[storage]` move with it. A `[plugins.cas]` table of the file wins: the old keys then go, with the warning, and change nothing.
- In `config.toml`, `max_evaluations` is `evaluations` in `[plugins.executor.pools.serve]`. A value that `[plugins.executor.pools.serve]` sets too wins.
- In `config.toml`, `tick_seconds` does nothing: the daemon wakes on events, not on a timer.
- In `config.toml`, `[plugins.network] name_claim` of the `proxy` network is `name_claims`, a list of one. A `name_claims` that the table sets too wins.

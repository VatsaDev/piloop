---

Run `piloop --help` for the list of commands, and `piloop <command> --help` for the options of one command.

Many commands take a `REF`: a campaign name, or a path inside the campaign's repo. Without a `REF`, `piloop status`
and `piloop history` use the campaign of the current directory, else the only active campaign, else every campaign.
`piloop inbox`, `piloop inbox wait` and `piloop watch` cover every campaign.

Commands that write sign their writes with `PILOOP_ACTOR` (`human` by default). See
[Environment variables](/reference/environment).

## Set up

### piloop init

```text
piloop init [PATH] [--example enwik8|titanic-tracks]
```

Makes `PATH` (default `.`) a piloop campaign and registers it. It is safe to run again.

- Runs `git init` and makes a baseline commit when necessary.
- When there is no `piloop.toml`, writes `piloop.toml`, `brief.md` and `evaluate.py` from the template. It keeps
  files that exist already. While `evaluate.py` is the unchanged stub, it stops and says what to edit.
- Measures `HEAD` as the baseline candidate and registers the campaign. When the campaign is registered already, it
  reads `piloop.toml` again.
- Copies the documents that `[memory] documents` names into the database. See
  [research memory](/concepts/research-memory).

`--example` creates a bundled example instead of the blank template.

### piloop install-skills

Copies the skills of this CLI into the skill directory of every harness on your `PATH`: `~/.claude/skills` for
Claude Code (or `$CLAUDE_CONFIG_DIR/skills`), and `~/.agents/skills` for Codex, pi, Gemini CLI and Cursor. It replaces
only piloop's own skills. The installer and `piloop upgrade` run it.

### piloop doctor

Checks the install, without changing anything. Each failure says how to fix it, often with the command to run. See
[Upgrading](/guides/upgrading#check-the-install).

### piloop plugins

Lists each capability (runtimes, storage backends, triggers, roles, and any that a plugin adds) with every provider,
the package and version that it comes from, and its entry point. Then it lists what the configuration selects: each
provider with where the choice comes from. It checks them as the daemon does when it starts, and fails as the daemon
would. See [How piloop loads plugins](/architecture/extension-points#how-piloop-loads-plugins).

### piloop upgrade

```text
piloop upgrade [--timeout SECONDS]
```

Upgrades the CLI, the skills and the database, and restarts a running daemon in place. `--timeout` (default 30) is
how long to wait for the daemon to come back. See [Upgrading](/guides/upgrading).

### piloop migrate

Brings the database to the schema of this CLI and prints what changed. The daemon and every command that reads or
writes campaigns do this silently when they start. `piloop doctor` and `piloop sql` do not.

## The daemon

### piloop serve

```text
piloop serve [--detach] [--check]
```

Runs the daemon in the foreground. `--detach` starts it in the background, with its output in
`$PILOOP_HOME/serve.log`. Only one daemon runs for each `PILOOP_HOME`. `--check` starts nothing: it checks what the
daemon checks when it starts, its plugins and what `config.toml` binds, and fails with the reason when it would not
start. See [How piloop loads plugins](/architecture/extension-points#how-piloop-loads-plugins).

### piloop stop

```text
piloop stop [--timeout SECONDS]
```

Sends SIGTERM to the daemon and waits up to `--timeout` seconds (default 30) for it to exit. The daemon stops the
running agents, and their runs fail with `daemon stopped`. Their ideas go back to `ready`. A run whose implementer already
left its finding is finished, not stopped: the next `piloop serve` scores its commits, and its idea does not run
again. The campaigns stay active, and the next `piloop serve` continues them. A campaign ends only at its `[stop]`
limits.

### piloop campaign stop

```text
piloop campaign stop REF [--kill] [--reason TEXT]
```

Stops a campaign. The daemon stops it on its next tick, as when a [`[stop]` condition](/concepts/cost) holds: it
drops the queued runs and the requested agents, the `stopped` triggers request the closing review, and each running
implementer is told to commit and stop, then ended 10 minutes later. What the implementers committed is scored. With `--kill`,
the implementers are ended at once, without the prompt, and their commits are still scored. On a stopped campaign, `--kill`
ends the implementers that are still winding down. `--reason` goes into `stopped_reason`, after who stopped it. It also stops a campaign that
is paused or held at its `[spend]` limit. A paused campaign gets its closing review; a held one as `[spend]
closing_review` says ([Cost and spend limits](/concepts/cost#spend-outside-piloop)).

### piloop restart

```text
piloop restart [--timeout SECONDS]
```

Restarts the running daemon in place on the installed code. The process keeps its pid, its environment and its
service manager. The running agents continue, and the new code connects to them again. `--timeout` (default 30) is how
long to wait for the daemon to come back. It first checks, as `piloop serve --check` does, that the daemon can start
again; when it cannot, it says why and leaves the daemon running.

### piloop service-unit

Prints a systemd user unit (Linux) or a launchd agent (macOS) that keeps `piloop serve` running. It installs nothing.
See [Running for days](/guides/running-for-days#under-a-service-manager).

## Pause a campaign

### piloop pause

```text
piloop pause REF --reason TEXT [--evals]
```

Pauses one campaign. The daemon queues no run, requests no role and launches no requested agent, so research files no
ideas. A sweep that is running already files its new and developed ideas as `proposed`, for a review. Running work
goes on, and its commits are scored. Nothing is escalated. The daemon still measures what a new evaluator or
`piloop candidate remeasure` needs, so the pause can end on a measured head. `--evals` holds those measurements too.
The pause is a state of the campaign in the database (`campaigns.paused`), not a file, so it holds wherever you run the
command. `piloop status` shows it with the reason. The paused time does not count toward `[stop] max_hours`, and no
`[stop]` condition is checked while paused.

A pause launches no agent at all, so no watchdog sweep starts for an anomaly of the running work either: the anomaly
shows in `piloop status`, and the watchdog gets it after `piloop resume`. The running agents keep their timeouts.

### piloop resume

```text
piloop resume REF
```

Ends the pause. The daemon queues runs and requests roles again on its next tick.

## Ideas and candidates

### piloop idea add

```text
piloop idea add REF TITLE [options]
```

Adds a defined idea. A `ready` idea runs when an implementer slot is free, in order of priority.

| Option | Meaning |
|---|---|
| `--hypothesis` | Why the idea should help, and by how much. |
| `--plan` | Concrete steps for the implementer. |
| `--from` | What prompted the idea, with ids or a URL. |
| `--family` | The mechanism family. Ideas that try the same mechanism share it. |
| `--priority` | 0 (urgent) to 4 (someday). Default 2. |
| `--harness` | Pin a harness instead of the rotation. |
| `--base` | The candidate id to start from, instead of the head. |
| `--proposed` | Wait for a human to approve the idea. |
| `--track` | The track. Required when the campaign has several. |
| `--after` | An idea to wait for. Repeat it for several. |
| `--supersedes` | An idea that this one refines. Repeat it for several. |

Research, the orchestrator and humans add ideas. A watchdog files a seed with `piloop idea seed` instead, and an implementer
files neither.

### piloop idea seed

```text
piloop idea seed REF HUNCH --from POINTERS [--base CANDIDATE] [--track TRACK]
```

Files a seed: a hunch in one line, with pointers to what prompted it. The research agent develops it into an idea,
or rejects it. See [Seeds](/concepts/ideas-and-runs#seeds).

### piloop idea develop

```text
piloop idea develop IDEA_ID --hypothesis … --evidence … --check … --metric … --effect … [options]
```

Develops a seed into a defined idea. Every one of these is required:

| Option | Meaning |
|---|---|
| `--hypothesis` | The mechanism, and why it should move the metric. |
| `--evidence` | What supports it, with ids and paths. |
| `--check` | The cheapest measurement that could kill it, and the result that stops the run. |
| `--metric` | What decides success: the primary metric, or the part of it that the idea targets. |
| `--effect` | The expected size of the effect, in the metric's units, and why. |

Optional: `--plan`, `--title`, `--family`, `--base`, `--priority` (default: the seed's), `--proposed`, `--after` and
`--supersedes`. As with `idea add`, the links are written together with the idea, so the daemon never takes the idea
without them.

### piloop idea status

```text
piloop idea status IDEA_ID STATUS --reason TEXT
```

Sets the status of an idea to `proposed`, `ready`, `parked`, `rejected` or `done`, with a note on the idea that says
why. `done` settles an idea without a run, so the ideas after it can start. A seed is developed first, and an idea
whose run is open (queued, running or being scored) can only be parked or rejected: `ready` would queue a second run,
and `done` would start the ideas after it before its run is judged. A parked or rejected idea's open run finishes and
is scored.

### piloop idea link

```text
piloop idea link IDEA_ID after|supersedes TARGET_ID --reason TEXT
```

Links an idea that exists to another idea of the same campaign: it waits until the target is `done` (`after`), or it
refines it (`supersedes`). The link is written in one transaction, so the daemon never takes the idea without it. An
idea whose run is open takes no `after` link, and a link that closes a cycle of its kind is refused. The `--after` and
`--supersedes` of `idea add` and `idea develop` are checked the same way.
`piloop idea unlink IDEA_ID after|supersedes TARGET_ID --reason TEXT` deletes a link, for example to a prerequisite
that was rejected and blocks the idea.

### piloop idea base

```text
piloop idea base IDEA_ID CANDIDATE_ID|head --reason TEXT
```

Pins the candidate that the idea's runs start from, or clears the pin with `head`: an unpinned run starts from the
head at the time it starts. A run that is open keeps its base, and the next attempt takes the new one.

### piloop idea track

```text
piloop idea track IDEA_ID TRACK --reason TEXT
```

Moves an idea to another track of `piloop.toml`, with a note on the idea that says why. An idea whose run is open
keeps its track, because the run's commits are judged on it.

Each of these commands writes its reason in a note on the idea. The change log records the change, signed with
`PILOOP_ACTOR`, whether a command or raw SQL made it: `idea.status`, `idea.track` and `idea.base_candidate_id` with
the old and new value, and `idea.linked` and `idea.unlinked` with the target and the kind.

### piloop candidate remeasure

```text
piloop candidate remeasure CANDIDATE_ID
```

Asks the daemon to measure the candidate again with the current evaluator, for a measurement that a fault of the host
spoiled, or for one more repeat, also on a stopped campaign. A `crash` that the daemon judged is judged again. Any
other verdict stays. The command says when the daemon measures it: not while the campaign is paused with `--evals`, or
held by its stop rule. See
[Measure a candidate again](/concepts/verdict#measure-a-candidate-again).

### piloop eval queue

```text
piloop eval queue
```

Lists the running evaluations, then the waiting ones in the order in which they get a slot. A requested remeasure
shows as `waiting` at once. See
[The evaluation queue](/concepts/verdict#the-evaluation-queue).

### piloop eval cancel

```text
piloop eval cancel CANDIDATE_ID
```

Cancels the evaluation of a candidate. A waiting one never starts, and the daemon stops a running one. It also cancels
a requested remeasure. The candidate gets a crashed measurement that names you.

### piloop candidate import

```text
piloop candidate import REF COMMIT [--summary TEXT]
```

Registers the tree of a commit, branch or tag of the repo as a `reference` candidate: a starting point that an idea
can pin with `--base`. The daemon measures it. It is never kept, never the head and never a bar. To import a candidate
of another campaign, fetch its commit into this repo first: `git fetch <its repo> <sha>`.

### piloop candidate note

```text
piloop candidate note CANDIDATE_ID REASON [--follow-up HUNCH]... [--track TRACK]
```

Keeps a measured `discard` or `interesting` candidate in view as a starting point. Its verdict becomes `interesting`,
and its reason becomes `note: <REASON>`, followed by the earlier reason. Each `--follow-up` files a seed pinned to the
candidate. See [Notes](/concepts/verdict#notes).

### piloop candidate verdict

```text
piloop candidate verdict CANDIDATE_ID keep|interesting|discard|crash --reason TEXT
```

Overrides the judgement of a candidate. The verdict is then yours, so the daemon never changes it. The
`candidate.verdict` event records the old and new verdict, with the reason. Only a judgement is overridden: a
`pending` candidate (the daemon is judging it), a `reference`, and an `unmeasured` or `recovered` one are refused. A
keep of a trunk run must build on the head (its commit has the head's changes, in its history or cherry-picked),
because the head is the newest trunk keep: a keep without the head's changes would drop them. A keep of a branch run
never moves the head.

### piloop measurement add

```text
piloop measurement add CANDIDATE_ID --report FILE
```

Records a measurement that you made yourself, for example by running the evaluate command on the candidate's commit,
under the campaign's current evaluator. `FILE` is JSON: `{"metrics": {"<name>": <value>}, "seconds": <s>, "error":
"<why>"}`. Every metric name must be one of `piloop.toml`, and every metric is needed unless `error` says why the
evaluation failed. A `pending` candidate is refused: add the measurement once the daemon has judged it. When the
candidate's verdict is the daemon's `crash`, `discard` or `interesting`, the daemon judges it again with every
measurement under the current evaluator, the next time it measures the campaign, also when the campaign is stopped:
not while it is paused with `--evals`, or held by its stop rule. Any other verdict stays, and a keep's mean, which the runs that
start from it must beat, includes the new measurement. The command says which of these happens.

## Status and the inbox

### piloop status

```text
piloop status [REF] [--json]
```

Prints the daemon's state, then for each campaign: the head, the tracks, the trajectory, the progress against
`[stop]`, the open runs, the queue, the running agents with their last line, the recent candidates, the anomalies,
the inbox, the latest decisions and the recent events. The watchdog and research agents get the same overview in
their brief.

`--json` prints one JSON document instead: the daemon's pid and the main facts of each campaign, read at one cursor of
the [event feed](/reference/event-feed).

### piloop events

```text
piloop events [--after CURSOR] [--campaign REF] [--kind KIND]... [--limit N] [--follow] [--timeout SECONDS] [--json]
```

Prints the events after `CURSOR` (default 0, the start of the feed), oldest first, at most `--limit` (default 100,
at most 1000), then the cursor to read after next. `--campaign` keeps the events about rows of one campaign, and
`--kind` the events of a kind; repeat it for several. The next cursor passes every event that the read examined,
also those that the filters left out. `--follow` waits, up to `--timeout` seconds (default 1800), until an event
arrives. `--json` prints one JSON document. See [Event feed](/reference/event-feed).

### piloop watch

```text
piloop watch [REF]
```

Shows the campaign on one screen, with keys to act on it. See [Watching a campaign](/guides/watch).

### piloop history

```text
piloop history [REF]
```

Prints the research pack: the metrics, the ideas by source, the analysis files, what was tried for each mechanism, the
latest 60 ideas with their outcomes, the kept lineage, the findings, the digests and the open escalations. A research
sweep reads it before it proposes ideas.

### piloop inbox

```text
piloop inbox [REF] [--kind KIND]... [--all] [--json]
```

Lists the unacknowledged items addressed to you, most urgent first, then the seeds that wait for research. `--kind`
keeps only items of the given kind: `note`, `finding`, `decision` or `escalation`. Repeat it to keep several kinds.
`--all` includes acknowledged items. `--json` prints them as one JSON document, read at one cursor of the
[event feed](/reference/event-feed). See [The orchestrator and the inbox](/concepts/orchestrator).

### piloop inbox show

```text
piloop inbox show COMMENT_ID
```

Prints one item, then the comments linked to it: the comments it cites, the comments that cite it, and its replies.

### piloop inbox ack

```text
piloop inbox ack IDS...
piloop inbox ack --up-to ID [--campaign REF] [--kind KIND]...
```

Marks items as seen. `--up-to` marks every unacknowledged item up to that id instead. With `--up-to`, `--campaign`
keeps only the items of one campaign, and `--kind` keeps only the items of the given kinds. With `IDS`, `--campaign` and
`--kind` are refused.
Nothing waits on an acknowledgement. To revise a decision, write a `decision` comment on its target.

### piloop inbox wait

```text
piloop inbox wait [REF] [--after EVENT_ID] [--timeout SECONDS]
```

Blocks until something needs the orchestrator, then prints it, one line each, and the command for the next wait. It
returns for a new inbox item that someone else wrote, a seed that someone else filed, a campaign that the daemon stopped,
an anomaly that the daemon gave to a watchdog, and the daemon's verdict on a measured candidate. `--after` is the cursor
that the last wait printed (default: now). `--timeout` (default 1800) is how long to wait before it returns with
nothing. Set the timeout of your shell tool above it.

### piloop wake

```text
piloop wake [--budget TOKENS]
```

Prints what an orchestrator session needs first, in a fixed budget (default 2000 tokens, about 4 characters each; 0
prints nothing): the latest lines of the journal, the open inbox, the head of each active campaign, and the current
lessons on their repos. Each section says how to read what did not fit. Run it at the start of every orchestrator
session.

### piloop journal

```text
piloop journal LINE
```

Adds one line, at most 280 bytes, to the orchestrator's journal: a decision, a plan or a result, with its ids. The
journal is append-only. `piloop wake` prints the latest lines, so that a new session picks up where the last one
stopped.

## Agents

### piloop launch

```text
piloop launch REF ROLE [--harness NAME] [--model MODEL] [--reason TEXT]
```

Asks the daemon for one more agent of `ROLE`, a sweeping role: `watchdog`, `research`, `scout` or a
[role that you defined](/concepts/roles#define-a-role). The daemon starts it on its next tick, within the role's
`max_concurrent`.
Only the daemon starts implementers, because an implementer needs a run.

### piloop attach

```text
piloop attach AGENT_SESSION_ID
```

Shows a running agent in this terminal. The [runtime](/concepts/runtimes) of the agent defines how. When the runtime
cannot, the command says so and tells you where to look instead.

### piloop prompt

```text
piloop prompt AGENT_SESSION_ID TEXT
```

Queues `TEXT` for the next turn of a running agent of any role. The [runtime](/concepts/runtimes) of the agent
defines how the message reaches it. When the runtime cannot deliver it, the command says why. The agent session ids are in
`piloop status`.

### piloop run cancel

```text
piloop run cancel RUN_ID [--wrap-up]
```

Cancels a queued or running run on the daemon's next tick. A queued run never starts, and a run whose implementer fails to
start is not launched again. A running implementer is ended with
[every process that it started](/concepts/runtimes#when-an-agent-ends), also those in sessions of their own. With `--wrap-up`, the implementer is first told to
commit and stop, and ended 10 minutes later. The run closes as `cancelled`, unless its implementer left its finding.
Its commits are scored, it counts toward no run limit, and its idea is parked: set the idea `ready` to run it again.

### piloop agent cancel

```text
piloop agent cancel AGENT_SESSION_ID [--wrap-up]
```

Cancels an agent of any role on the daemon's next tick: a sweep, or an implementer, whose run it cancels as
`piloop run cancel` does. A requested agent never starts. A running one is ended with every process that it started,
at once or, with `--wrap-up`, after it was told to commit and stop.

## The database

### piloop sql

```text
piloop sql STATEMENT|-
```

Runs one SQL statement against the piloop database. Schema changes, transactions, `ATTACH` and all but the read-only
`PRAGMA`s are denied. So are writes to piloop's internal tables and to the full-text indexes. Everything else,
including `DELETE`, is allowed. The output stops at 500 rows. See the [database schema](/reference/schema).

With `-`, the statement is read from stdin, so a text with backticks, `$(…)` or `$VAR` reaches the database unchanged.
Pipe it in from a quoted heredoc, which the shell does not expand:

```bash
piloop sql - <<'EOF'
INSERT INTO comments (target_kind, target_id, author, kind, body)
VALUES ('idea', 12, 'human', 'note', 'Run `make bench` first: it''s the slow step.');
EOF
```

### piloop schema

Prints what `piloop sql` accepts, the conventions for writing to the database, and every table. Agents read it before
they write.

## The workspace archive

### piloop restore

```text
piloop restore REF [IDEA | PATH]
```

Writes archived workspace files back into the campaign's workspace. `IDEA` (`12` or `idea#12`) restores the files of
that idea. `PATH` restores one workspace-relative file or everything under a directory. With neither, it restores
every archived file. A file that is already there with other content is kept and listed, never overwritten. See
[The artifact store](/concepts/artifact-store).

### piloop store status

Prints what the store holds (blobs, their local size, how many are on the remote), how much of each campaign was
archived, and how many done ideas and stopped campaigns are still due.

### piloop store evict

Uploads the blobs that the remote does not have yet, then drops local copies as `[storage]` says. The daemon does this
every hour.

### piloop store verify

```text
piloop store verify [REF]
```

Checks that the store holds every blob of every archive: local copies are hashed again, evicted ones are looked up on
the remote. Exits non-zero when one is missing or corrupt.

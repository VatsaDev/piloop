Every agent that piloop starts has a **role**. Every agent is a coding agent CLI (a **harness**: Claude Code, Codex or
pi) that runs in a git worktree of the project, with a brief, and reads and writes the piloop database. piloop has
four built-in roles. You can [define more](#define-a-role) in `piloop.toml`.

| Role | What it does | When the daemon starts one | Its worktree |
|---|---|---|---|
| **worker** | Implements one idea and commits. | A ready idea and a free worker slot. | At the starting point of its run. Its commits are scored. |
| **watchdog** | Looks for problems and reports them. | On an anomaly, every `interval` seconds, and once when the campaign stops. | At the head. Its commits are not scored. |
| **research** | Develops seeds into ideas and adds ideas of its own. | A new seed, or a short backlog. | At the head. Its commits are not scored. |
| **scout** | Searches outside the repo for techniques and files them as seeds. Experimental. | Every `interval` seconds, when you set it. Off by default. | At the head. Its commits are not scored. |

Every role has the same lifecycle. The daemon writes a `workers` row, starts the agent, waits until the agent ends or
times out, saves the screen transcript, reads the tokens that the agent used, attaches the session to
[Entire](/concepts/session-capture), and closes the row. `piloop status` lists the running agents with their ids.

The worker **does runs**: the run queue starts it, it works at the starting point of its run, and its commits are
scored and judged when it ends. A role that you define can do runs too ([Define a role that does
runs](#define-a-role-that-does-runs)). Every other role is a **sweeping** role. Its triggers start it, it works at the
head or in the project checkout, and nothing is scored when it ends.

The [orchestrator](/concepts/orchestrator) is not a role. The daemon never starts it.

## Triggers

A trigger is a condition that the daemon checks on each tick, for each project. When a trigger of a sweeping role
fires, the daemon requests one more agent of that role. The agent's brief shows the reason. Each entry of `triggers` is
a table with the trigger's `kind` and its parameters:

<Triggers />

The daemon checks the triggers in the order of the list. It requests at most one batch for each role on each tick,
and it requests nothing while a request of the role waits to start. An `anomaly` fire changes what the agent does,
so it gets an agent of its own: it fires alone when it is the first trigger to fire, and otherwise waits for a later
tick. While the campaign runs, the daemon checks every trigger except `stopped`. On the tick that stops the campaign,
it checks only `stopped`.

A `sql` query can use two parameters: `:project`, the project's id, and `:since`, when the role's last agent started.
Compare `:since` with a `created_at` column to fire only on what is new. `piloop init` checks the query on an empty
copy of the database: it must be one statement that only reads.

Change the triggers of a built-in role with its `triggers` key. For example, this watchdog does not investigate
anomalies. It reviews progress every hour, and once when the campaign stops:

```toml
[roles.watchdog]
triggers = [{ kind = "cron" }, { kind = "stopped" }]
interval = 3600
```

An empty list turns the triggers off, the closing review included. The role then starts only when you ask
(`piloop launch`).

## Define a role

A table with a new name defines a new sweeping role. It needs `prompt`, the file that starts its brief, and
`triggers`. The other keys have the defaults of the [configuration reference](/reference/configuration#sweeprole).
This reviewer reads each new keep and files a seed when it finds a problem:

```toml
[roles.reviewer]
prompt = "briefs/reviewer.md"   # relative to the repo root
triggers = [
  { kind = "sql", when = "SELECT id FROM candidates WHERE project_id = :project AND verdict = 'keep' AND created_at > :since" },
]
workdir = "head"
runtime = "subprocess"
max_concurrent = 1
timeout = 900
files = "seeds"
writes = ["comments(finding) on a candidate", "seeds via idea seed"]
```

The brief of a reviewer is your prompt, then `brief.md`, the database procedures and its context: its signature
(`reviewer#<worker id>`), the reason it started, the project overview and the research pack. A sweep that got
anomalies has the incidents instead of the research pack. `incident_prompt` and `routine_prompt` add a file after
your prompt for each kind of sweep, as the watchdog does. With `files = "ideas"`, the context also says how many ideas
the sweep may add (`max_ideas`), which `low_water` counts on. Run `piloop init` after
you change the table. `piloop launch <project> reviewer` asks for one more reviewer by hand.

A role name has at most 20 characters: lowercase letters, digits, `_` and `-`, and a letter first. `run`,
`orchestrator`, `human` and `daemon` are taken.

A Python package can also add roles and triggers. See
[Extension points](/architecture/extension-points#roles).

## Define a role that does runs

A table with a new name and `runs = true` defines a role that does runs. It takes the worker's defaults, its prompt
included, so every key is optional. This role takes the cheap ideas, with a short timeout and its own harness:

```toml
[roles.quick]
runs = true
takes = "priority >= 3"    # an SQL condition on the ideas table; unset: every runnable idea
prompt = "briefs/quick.md" # unset: the worker's prompt
harnesses = ["pi"]
timeout = 300
max_concurrent = 2
explore_every = 0
```

On each tick, the roles that do runs fill their free slots in order: the roles that you define, in the order of the
file, then the worker. So the worker takes every idea that the other roles leave. This includes an idea that waits
for a free slot of a full role. To keep the worker away from the cheap ideas, give it a condition too, for example
`[roles.worker] takes = "priority < 3"`.

Some rules apply to each role that does runs, and some to every run of the project:

- Each role: its own `max_concurrent`, its `takes`, its harness rotation, its prompt and timeout, its `explore_every`
  (counted over its own runs), and the track shares (of its own slots).
- Every run: `[stop] max_runs` and `plateau`, the attempts of an idea (`ideas.max_runs`), and the verdict. A keep of
  a run of any role moves the head. A keep against a bar that the head left behind is merged onto the head in the same
  way.
  `low_water` keeps a backlog of one idea per run slot of every role, plus its `buffer`.

`runs.role` records the role of each run, and its agents have that `workers.kind`. When `piloop init` removes a role,
its queued runs fail. They do not count as attempts, so their ideas go back to the queue.

## Worker

A worker gets one idea. Its brief has the worker instructions, your `brief.md`, the idea, the starting point and the
recent results. It may edit the code in its worktree and commit. It writes a `finding` comment on its idea at the end.
It must not change the rows of runs, candidates or measurements, and it files no ideas or seeds.

## Watchdog

The watchdog informs. It never edits code or changes a row. It writes comments: findings, notes and escalations for
the orchestrator, and seeds for research. It runs in one of two modes:

- An **incident sweep**, when the daemon detects an anomaly. Anomalies are a failed or timed-out run, a worker or
  research agent that died at startup, and a worker with no comment or commit for an hour while its jobs run. Its
  brief adds `watchdog_incident.md`, the watchdog's `incident_prompt`.
- A **progress review**, every `[roles.watchdog] interval` seconds. It asks whether the campaign is getting
  closer to its goal. Its brief adds `watchdog_progress.md`, the watchdog's `routine_prompt`. When the campaign
  stops, the `stopped` trigger asks for one last progress review, which writes the closing report.

## Research

The research agent keeps the workers supplied with ideas. A sweep:

1. Reads the **research pack** that the daemon builds: the metrics, what each source of ideas produced, the analysis
   files listed in the project's `context`, what was tried for each mechanism, the latest 60 ideas with their
   outcomes (and the total count), the kept lineage, and the findings of every role on the project. `piloop history`
   prints the same pack.
2. Develops each waiting seed into an idea, or rejects it with the reason.
3. Adds ideas of its own, up to `max_ideas`, where the head loses the most.
4. Writes one `finding` on the project.

The daemon starts a research sweep when:

- A seed is filed.
- The backlog is short (`low_water`): fewer ready ideas than one per run slot plus the trigger's `buffer`. When a sweep
  adds no idea, research waits longer before the next one.

Ask for a sweep at any time with `piloop launch <project> research`.

## Scout

<Note>Experimental: the scout.</Note>

A **scout** sweep searches outside the repo for techniques that could reduce a measured loss:

1. It writes a problem statement first: the open problems as measured losses, what was tried, and the constraints.
2. It searches X, GitHub and arXiv by problem. It also checks a watch list: the X accounts and GitHub repos whose
   earlier seeds paid off. It uses no curated list of people.
3. It ranks the results by substance: a number against a baseline, code, a method, an ablation.
4. It files at most `seeds` of them as seeds, signed `scout#<worker id>`. The others go to the technique library, the
   `techniques` table. Research develops the seeds or rejects them.
5. It writes one `finding` on the project, at priority 3, so that it reaches your inbox.

The scout is off until you set its `interval`:

```toml
[roles.scout]
interval = 86400   # seconds between scout sweeps
seeds = 3          # seeds that one scout sweep may file
```

Ask for one scout sweep with `piloop launch <project> scout`. A search tool for X needs an MCP server in the scout's
`mcp`; see [MCP servers](/guides/mcp-servers).

## Ask for one more agent

`piloop launch <project> research` (or `watchdog`, `scout`, or a role that you defined) asks the daemon for one more
agent of that role. The daemon starts it on its next tick, within `max_concurrent`. Use `--harness` and `--model` to choose the agent's harness and model,
and `--reason` to add a line to its brief.

An agent can do the same with SQL. The `workers` table is the launch queue:

```sql
INSERT INTO workers (kind, project_id, state, reason) VALUES ('research', 1, 'requested', 'second opinion on idea#40')
```

## Look at an agent

- `piloop watch` shows the agents with their last output.
- `piloop attach <worker-id>` shows the agent in this terminal.
- `piloop prompt <worker-id> "<text>"` queues a message for the agent's next turn.

The [runtime](/concepts/runtimes) of the agent defines how `piloop attach` and `piloop prompt` do this. When the
runtime cannot, the command says so and tells you where to look instead.

Each agent's brief, log and transcript are in `~/.piloop/runs/<run>/` for an agent that does a run, and in
`~/.piloop/workers/<worker-id>/` for the sweeping roles.

Every agent that piloop starts has a **role**, which says what the agent does and when it starts. The agent is a
**harness**, a coding agent CLI (Claude Code, Codex or pi), in a git worktree of the campaign. piloop has four roles:

| Role | What it does | When the daemon starts one | Its worktree |
|---|---|---|---|
| **implementer** | Implements one idea and commits. | A ready idea and a free implementer slot. | At the starting point of its run. Its commits are scored. |
| **watchdog** | Looks for problems and reports them. | On an anomaly, every `interval` seconds, and once when the campaign stops. | At the head. Its commits are not scored. |
| **research** | Develops seeds into ideas and adds ideas of its own. | A new seed, or a short backlog. | At the head. Its commits are not scored. |
| **scout** | Searches outside the repo for techniques and files them as seeds. Experimental. | Every `interval` seconds, when you set it. Off by default. | At the head. Its commits are not scored. |

Each agent that the daemon starts is an **agent session**, with an id, a log and the tokens that it used.
`piloop status` lists the live ones, for example `implementer#12`.

The implementer **does runs**: it takes ideas from the run queue, and its commits are scored. The other roles are
**sweep roles**: their triggers start them, and nothing that they commit is scored. The
[orchestrator](/concepts/orchestrator) is not a role. The daemon never starts it.

## Configure a role

Each role has a table in `piloop.toml`. This one runs up to four implementers on two harnesses, for at most 30 minutes
each, and one research agent at a time:

```toml
model = { claude = "claude-opus-5-5", codex = "gpt-6.1-sol" }

[roles.implementer]
harnesses = ["claude", "codex"]
max_concurrent = 4
timeout = 1800

[roles.research]
max_concurrent = 1
```

The [configuration reference](/reference/configuration#roles) lists every key and its default. The top-level
`max_concurrent` table limits one harness across every role, for example `max_concurrent = { claude = 2 }` when your
account limits the request rate.

## Triggers

A **trigger** is a condition that the daemon checks on each **tick**, a pass of its loop every 2 seconds. When a
trigger of a sweep role fires, the daemon starts one more agent of that role, and the agent's brief says why:

<Triggers />

The `triggers` key of a role sets its triggers. This watchdog does not investigate anomalies. It reviews the progress
every hour, and once when the campaign stops:

```toml
[roles.watchdog]
triggers = [{ provider = "cron" }, { provider = "stopped" }]
interval = 3600
```

An empty list turns the triggers off. The role then starts only when you ask, with `piloop launch`.

A `sql` trigger can use two parameters: `:campaign`, the campaign's id, and `:since`, when the role's last agent
started. `piloop init` refuses a query that is not one statement that only reads.

## Define a role

A table with a new name defines a sweep role. It needs `prompt`, the file that starts its brief, and `triggers`. This
reviewer reads each new keep and files a seed when it finds a problem:

```toml
[roles.reviewer]
prompt = "briefs/reviewer.md"
triggers = [
  { provider = "sql", when = "SELECT id FROM candidates WHERE campaign_id = :campaign AND verdict = 'keep' AND created_at > :since" },
]
max_concurrent = 1
timeout = 900
files = "seeds"
writes = ["comments(finding) on a candidate", "seeds via idea seed"]
```

Its brief is your prompt, then `brief.md`, the database procedures, the reason that it started, and the research pack.
Run `piloop init` after you change the table. `piloop launch enwik8 reviewer` asks for one more reviewer.

A role name has at most 20 characters: lowercase letters, digits, `_` and `-`, with a letter first. `run`,
`orchestrator`, `human` and `daemon` are taken. A plugin can also add roles and triggers. See
[Extension points](/architecture/extension-points#roles).

## Define a role that does runs

A table with a new name and `runs = true` defines a role that does runs. It has the implementer's defaults, so every
other key is optional. This role takes the cheap ideas, with its own harness and a short timeout:

```toml
[roles.quick]
runs = true
takes = "priority >= 3"    # an SQL condition on the ideas table
harnesses = ["pi"]
timeout = 300
max_concurrent = 2
```

The roles that you define take their ideas first. The implementer takes every idea that they leave, also one that
waits for a slot of a full role. To keep the implementer away from the cheap ideas, give it a condition too:
`[roles.implementer] takes = "priority < 3"`.

Each role that does runs has its own `takes`, harnesses, prompt, timeout and slots. The stop rule's limits, the attempts
of an idea and the verdict count every run of the campaign. A keep of any role moves the head.

## The built-in roles

- The **implementer** gets one idea, with your `brief.md`, the starting point and the recent results. It edits the
  code and commits. At the end, it writes a `finding` comment on its idea. It files no ideas or seeds.
- The **watchdog** edits no code and changes no row. It writes comments for the orchestrator, and seeds for research.
  An **incident sweep** investigates an anomaly: a failed run, or an agent that died at its start. A **progress review** asks if the campaign gets closer to its goal. The last review, when the
  campaign stops, writes the closing report.
- The **research** agent reads the **research pack**: the metrics, what was tried for each mechanism, the recent ideas
  and their outcomes, the kept lineage, and the findings of every role. `piloop history enwik8` prints it. Research
  develops each waiting seed, adds ideas where the head loses the most, and writes one `finding`. It starts on a new
  seed, when the backlog has fewer ready ideas than one for each run slot, plus a buffer (`low_water`), and once per
  stall mark of runs without a keep (`stalled`).

## Scout

A **scout** writes the open problems as measured losses, then searches X, GitHub and arXiv for techniques that could
reduce them. It files the best few as seeds, and keeps the others in the `techniques` table. It is off until you set
its `interval`:

```toml
[roles.scout]
interval = 86400   # seconds between scout sweeps
seeds = 3          # seeds that one scout sweep may file
```

A search tool for X needs an MCP server in the scout's `mcp`. See [MCP servers](/guides/mcp-servers).

## Ask for one more agent

```bash
piloop launch enwik8 research --reason "second opinion on idea#2"
```

The daemon starts the agent on its next tick, within `max_concurrent`. `--harness` and `--model` choose the agent's
harness and model.

## Runtimes

A **runtime** is where an agent runs. It starts the agent, watches it, sends it messages and stops it. The `runtime`
key of `piloop.toml` sets it for the campaign, and `[roles.<name>] runtime` for one role.

## Look at an agent

- `piloop watch` shows the agents with their last output.
- `piloop attach <agent-session-id>` prints the last 40 lines that the agent wrote.
- `piloop prompt <agent-session-id> "<text>"` queues a message for the agent's next turn.

When the runtime of the agent cannot take the message, the command says why. The brief, log and
transcript of an agent are in `~/.piloop/runs/<run>/` for a run, and in `~/.piloop/agent_sessions/<id>/` for a sweep.

## When an agent ends

When an agent ends, piloop ends every process that the agent started, also one in a session of its own. So a shared
server that an agent starts, such as an sccache, Gradle or Bazel daemon, ends with the agent. Start it outside piloop
to keep it running.

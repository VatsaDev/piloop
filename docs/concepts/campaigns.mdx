A **campaign** is a git repo, an **evaluate command** that scores its code, and the metrics to improve. This is the
`piloop.toml` of the enwik8 example, without its limits:

```toml
name = "enwik8"
evaluate = ["uv", "run", "python", "evaluate.py"]
harnesses = ["claude"]
model = { claude = "claude-opus-5-5" }
link = ["data", ".venv"]

[[metrics]]
name = "bytes"
direction = "lower"
role = "primary"

[[metrics]]
name = "seconds"
direction = "lower"
role = "guardrail"
margin = 60
floor = 120
repeats = 3
```

`brief.md`, next to it, tells every agent what to improve and what it must not touch. `piloop init` registers the
campaign and stores a copy of `piloop.toml`. The daemon uses that copy, so run `piloop init` again after each edit. The
[configuration reference](/reference/configuration) lists every key.

## The evaluate command

piloop runs the evaluate command at the root of a clean worktree of each commit. The command prints one
`METRIC <name>=<value>` line for each metric:

```text
$ uv run python evaluate.py
METRIC bytes=3688775
METRIC seconds=0.69
```

piloop ignores the other output. A non-zero exit, a missing metric, or a run longer than `evaluate_timeout` seconds
makes the commit a `crash`. Print the reason on stderr. The measurement of a crash keeps the `METRIC` lines that it
printed, and never scores.

Make the command deterministic: fix the seeds and the data splits. In `brief.md`, tell the implementers not to edit
the evaluate command or the data.

<Warning>
  piloop runs the evaluate command from the commit that it measures. An implementer that edits the command changes its
  own score.
</Warning>

## Metrics

Each `[[metrics]]` table names one metric that the evaluate command prints, and its `direction`: `higher` or `lower`
is better. Its `role` says how the [verdict](/concepts/verdict) uses it:

- **primary**: the metric to improve. A campaign has one, or one for each [track](/concepts/tracks).
- **guardrail**: it may get worse by at most its `margin` for each keep, and never past its `floor`.
- **watch**: recorded only.

## Per-unit results

A metric is often a sum over units, such as test examples. When the evaluate command reports the result of each unit,
the verdict can tell a broad gain from a gain on a few lucky units.

piloop sets `PILOOP_UNITS_FILE` to a path when it measures a candidate. Write a JSON object there, with each unit's
part of each metric:

```json
{"accuracy": {"test-0001": 0.0056, "test-0002": 0.0, "test-0003": 0.0056}}
```

- The values of a metric must sum to its `METRIC` value, within 0.1%. For a mean over `n` units, divide each value
  by `n`.
- Leave out metrics that are not sums, such as a latency.
- A file that is not valid makes the evaluation fail.

The agents never see the file, so they cannot tune their code to single units.

## Evaluators

piloop never compares scores from two different evaluators. These words have one meaning each:

| Word | Meaning |
|---|---|
| evaluate command | Your program: the `evaluate` key. |
| **evaluator** | The evaluate command, `link`, and the names and directions of the primaries and guardrails. A change to one of these makes a new evaluator at the next `piloop init`. |
| **evaluation** | One run of the evaluator on a candidate. |
| **measurement** | The metric values that one evaluation recorded. |

After a new evaluator, the daemon measures the head again, and what the open runs need. The other keeps keep their
old scores. To measure one of them again, for example to compare the whole trajectory:

```bash
piloop candidate remeasure 2
```

A change to a margin, a floor or the verdict rule makes no new evaluator, and neither does a watch metric that you add,
remove or redirect: older measurements just lack it. These change how the next candidates are judged. Making a watch
metric a guardrail or a primary, or the reverse, makes a new evaluator.

## Shared files

- `link` lists paths that git ignores, such as `data` or `.venv`. Every worktree gets them read-only, as they were when
  its job was made. A write in place to a linked file fails. New files stay in the worktree.
- `workspace/` is a directory that every agent of the campaign shares, for notes, caches and plots. It is never
  committed. Each agent gets a read-only copy of it as it was when the agent started, on any machine. What the agent
  writes or removes there goes into the shared workspace when it ends. When two agents change one file, the first
  one's stays, and the second one's goes beside it, as `NOTES.md.implementer-12`.

## Where the results are

- Each commit of a run is a git ref under `refs/piloop/<campaign>/`, for example `refs/piloop/enwik8/r1/0`.
  `git show` and `git cherry-pick` work on it after its worktree is gone.
- The database holds the ideas, runs, candidates, measurements and comments. Read it with `piloop sql`. See the
  [database schema](/reference/schema).
- The briefs, logs and transcripts of the agents are under `~/.piloop/runs/` and `~/.piloop/agent_sessions/`.

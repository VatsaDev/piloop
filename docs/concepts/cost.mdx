A campaign costs money in two ways: the tokens that the agents use, and what the campaign pays outside piloop, such as
GPU time or paid APIs. piloop measures the first and enforces a limit on both.

## Tokens

When an agent ends, piloop reads the tokens that it used from the harness's own session file. This works for Claude
Code, Codex and pi. piloop writes the totals to `agent_sessions.usage`:

```json
{"input": 120345, "output": 18230, "cache_read": 950112, "cache_write": 40211, "total": 1128898, "turns": 41, "source": "…"}
```

- `piloop status` and `piloop watch` show the tokens of each campaign.
- The kept lineage shows the tokens that each candidate cost.
- `max_tokens` in `[plugins.stop_rule]` ends the campaign when the agents of the campaign have used that many tokens in
  total.

```toml
[plugins.stop_rule]
max_tokens = 50_000_000
```

For every harness, `input` is the input that the prompt cache did not serve, and `cache_read` and `cache_write` are
the cached input. `total` is the harness's own count of the session's tokens.

## Stop conditions

`[plugins.stop_rule]` sets the limits of the built-in stop rule, `limits`. Any one of them ends the campaign:

<Stop />

When a limit is reached, the campaign becomes `stopped`. The daemon tells the running implementers to commit and
stop, ends them 10 minutes later, and scores what they committed. It drops the queued runs and the requested agents.
Once the commits are scored, the watchdog's closing review writes the closing report. Without a limit, the campaign
has no end.

`piloop campaign stop <campaign>` stops a campaign by hand, the same way. A stop written with raw SQL
(`UPDATE campaigns SET status = 'stopped'`) skips the closing review. `piloop stop` stops the daemon, not the
campaign. To resume a stopped campaign, change its limits and run `piloop init`.

A plugin can add another stop rule, which `provider` in `[plugins.stop_rule]` selects:
[Stop conditions](/architecture/extension-points#stop-conditions) has an example.

## Spend outside piloop

piloop knows no vendor and no currency: what a campaign spends outside piloop is a **fact** like any other, which a
fact source reads. The built-in `command` source runs a command that prints `METRIC <name>=<value>` lines, as the
evaluate command does, and `hold_at` in `[plugins.stop_rule]` is a hard limit on any fact that it names:

```toml
[[facts]]
provider = "campaign"                          # piloop's own facts: list both when you add a source

[[facts]]
provider = "optimization"

[[facts]]
provider = "command"
command = ["uv", "run", "scripts/spend.py"]   # prints METRIC spend=412.3
metrics = ["spend"]                           # the names it prints
notices = { spend = [300, 600] }              # each one posts a note to the inbox when crossed

[plugins.stop_rule]
hold_at = { spend = 1000 }                    # nothing new starts at this spend
```

The daemon reads the source every `interval` seconds. `command` runs at the root of the repo with the daemon's
environment, so give it its keys there ([Secrets](/guides/secrets)). Each reading is a `fact.read` event on the
campaign. GPU hours, API calls or anything else is one more name in `metrics`. A plugin can add another source, for
example one that reads a cloud's billing API.

`limits` **holds** the campaign while a fact of `hold_at` is at its limit or above, and while it is not known: before
the first reading, and after a failed one. An unknown value is never read as zero. At the limit, `limits` posts one
escalation at priority 0, and the source posts one when its readings start to fail. While the campaign is held, the
daemon starts no agent and no evaluation for it. Agents and evaluations that already run finish, and their commits are
scored. A stop rule that reads a fact needs a source of it in `[[facts]]`, or piloop refuses the configuration.

A hold is not a stop: nothing is dropped. The hold ends on the first pass after the cause ends. To resume after the
limit, raise it in `hold_at` in `piloop.toml` and run `piloop init`. After a failure, fix the source; it reads again
every `interval`. A limit does not stop a held campaign.

`piloop campaign stop` stops a held campaign at once. `while_held` in `[plugins.stop_rule]` says what happens to the
closing review of that stop:

| `while_held` | What the daemon does |
|---|---|
| `"run"` (default) | It starts the closing review, also past the limit or with an unknown value. |
| `"skip"` | It starts no closing review. The stop ends at once, and the daemon posts an escalation that says so. |
| `"wait"` | It requests the closing review, and starts it when the hold ends. It goes on reading the facts until then. |

A paused campaign that you stop starts its closing review at once: a pause does not hold a stopped campaign.

`piloop status` shows each fact of `hold_at` against its limit, `spend 412.3/1000`, and why the campaign is held:
`spend 1012/1000 (launches held: spend at its limit)`. The `cost` section shows the spend per keep and per evaluation.
Tokens are not part of the spend, because piloop has no price table. Use `max_tokens` for them.

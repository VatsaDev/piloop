The **orchestrator** is a coding agent that runs the campaign for you. It answers what the other agents escalate,
manages the ideas, steers the implementers and reports. It is any coding agent with the `piloop-operate` skill: the
daemon never starts it, and works without one. To start one, open your agent in the campaign repo and ask it to
"orchestrate the piloop campaign".

The skills come with the CLI: the installer and `piloop upgrade` run `piloop install-skills`, so they always match it.

## The loop

The orchestrator waits on one command, so its model uses no tokens while nothing happens:

```bash
PILOOP_ACTOR=orchestrator piloop inbox wait enwik8 --timeout 1800
```

```text
candidate#2 keep: against candidate#1: bytes 2720458 vs 3688775 (-968317; 95% worst case -968317 over 3 pairs); guardrails…
campaign enwik8 stopped: max_runs: 1 runs
seed idea#3 (enwik8) by human: Combine the lzma preset of candidate#2 with a preprocessed dictionary — candidate#2
next: piloop inbox wait enwik8 --after 17
```

The wait returns on a new inbox item, a new seed, a verdict, an anomaly or a stop, or at the timeout. Its last line is
the next wait, with a cursor, so nothing is lost between two waits. `PILOOP_ACTOR=orchestrator` signs the
orchestrator's writes, and the wait skips them.

Run one orchestrator for each campaign. Two orchestrators answer the same escalation twice.

## Comments

Agents and humans talk through **comments** on a campaign, an idea, a run, a candidate or another comment. A comment
has a kind:

| Kind | Use |
|---|---|
| `note` | Context, or a short remark. |
| `finding` | A result: what an agent tried and learned. |
| `decision` | A decision, with the reason and how to revert it. |
| `escalation` | A question that needs a decision. |

A comment on an idea goes into the brief of the idea's next run.

## The inbox

The **inbox** is every comment that has a priority: 0 and 1 are urgent, 2 to 4 can wait. An escalation always has a
priority. A comment without one is not in the inbox.

```bash
piloop inbox                 # the open items, most urgent first, and the seeds
piloop inbox show 812        # one item and its thread
piloop inbox ack 812         # mark it as seen
```

## Decisions

Work should not wait for you, so the orchestrator decides what comes up. It records each decision that it takes for you
as a `decision` comment in your inbox:

```text
[<category>, reversible|irreversible] <what it decided, in one line>
Why: <the evidence, with ids>
Changed: <the rows, files, settings or commits>
Revert: <the command or edit that undoes it>
```

A change to a goal, a metric, a guardrail, the evaluate command or a stop condition has priority 0. A routine fix has
priority 3 or 4. A decision that cannot be undone and can wait, the orchestrator leaves to you as an escalation.

To revise a decision, reply to it in `piloop watch` (key `r`). The orchestrator's next wait returns your reply, and it
applies your reply first.

## Several campaigns

A campaign is one repo with its own `piloop.toml`. To improve two repos, set up two campaigns: open your agent in each
repo, or name the repo. One daemon serves every campaign of a `PILOOP_HOME`.

```text
Use piloop on ~/projects/search to cut the p95 latency of the query endpoint.
```

Two goals for the same code, such as the accuracy and the cost of one model, are [tracks](/concepts/tracks) of one
campaign, not two campaigns.

One agent can orchestrate every campaign. Ask it to "orchestrate all my piloop campaigns". Without a campaign name,
`piloop inbox wait`, `piloop inbox` and `piloop watch` cover every campaign, and each item names its campaign.

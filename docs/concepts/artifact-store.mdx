---
title: The artifact store
description: How piloop archives the shared workspace when it is done with it, and how to get files back.
---

Every campaign has one shared workspace, `$PILOOP_HOME/projects/<id>/workspace`. Agents leave notes, logs, evaluation
outputs and analysis arrays there. On a long campaign
it grows to hundreds of gigabytes, much of it copies.

piloop stores workspace files in a content-addressed **artifact store** once nothing needs them any more. It removes
the local copies later, and `piloop restore` brings them back.

## What is archived, and when

The daemon archives in the background, one job at a time. Its scheduling loop never waits for an archiving.

- **When a subject settles**, the entries named after it are archived: `workspace/<kind><id>…` (`idea12/`,
  `idea12-canary.log`). An idea settles when it is done and none of its runs is open, and again after each new run.
  The `subject.settled` event on the idea says so. Implementers are told to put their output there.
- **When a campaign stops** and none of its agents is alive any more, everything left in its workspace is archived.
- **Never archived**: `NOTES.md` and `research/` at the top of the workspace. These small knowledge files stay where
  research sweeps read them.

An archiving stores every file and symlink, stores a manifest that lists them, and checks that the store holds all of
it. Only then does it record the archiving in the `archives` table. It removes nothing: the local copies stay, so an
agent or a human that still reads a file, for example to answer an escalation, finds it.

## When local copies go

The daemon removes the workspace copies of an archiving later, and records when in `archives.pruned_at`:

- **By age**: 7 days after the archiving.
- **Under disk pressure**: while the disk of `PILOOP_HOME` has less than `[storage] min_free_gb` free, the oldest
  archivings first. Before them go the copies of `link` inputs that no running job uses, oldest first: the next job
  that needs one makes it again from the store.

It removes only a file that still holds what was stored (same size and hash), and a symlink that still points where
it did. A file that an agent wrote since stays, and so does its directory. It checks age and pressure every hour,
before the next archiving, and checks pressure again before it stores anything.

Storing a file writes its compressed copy first, so archiving needs room on the disk of the store. A workspace larger
than the free space above `min_free_gb` is stored in batches: before each batch, the daemon removes older local
copies while the disk is short, then measures the free space again. When not one more file fits, the rest is not
stored, and the daemon writes an `anomaly.disk` event on the campaign, with the bytes needed, the bytes free and the
reserve. Only the last batch of a job that stored everything marks the job as done (`archives.complete`). A job that
stops short, because of the disk, a failure or a stop of the daemon, stays due, and its next run stores the rest.
After a failed or deferred archiving the daemon waits 10 minutes before the next one.

Which archivings are due is computed from the event feed and the campaigns. A daemon that stops in the middle of a backlog picks it up
where it was when it starts again. Content that was already stored is found by its hash and is not stored twice.
`piloop store status` shows how many are still due.

## Getting files back

```bash
piloop restore my-campaign idea#12       # the files of idea#12; 12 for short
piloop restore my-campaign idea12/plots  # one path, or everything under it
piloop restore my-campaign               # everything
```

`piloop restore` reads the files from the local store, or downloads them from the remote. A file that is already in
the workspace with other content is kept and listed, never overwritten. Agents may run it too.

## How the store works

One store serves every campaign of a `PILOOP_HOME`, in `$PILOOP_HOME/store`.

- **Content addressing.** A blob is addressed by a [CID](https://dasl.ing/cid.html) of the BLAKE3 hash of its whole
  content. A file that appears in many places, or in two campaigns, is stored once.
- **Compression.** Blobs are kept zstd-compressed. JSON and logs shrink about tenfold; arrays that are already
  compressed (`.npz`) barely shrink.
- **Streaming.** Files of any size are read and written in 1 MiB pieces, never held in memory.
- **Manifests.** A manifest lists the paths of one archiving, each with its blob, size and mode (or a symlink's
  target). It is a [DASL](https://dasl.ing) value that links each blob, and the `archives` table records its CID.

Nothing is ever deleted from the store. There is no garbage collection.

## A remote store

`[plugins.cas]` in `$PILOOP_HOME/config.toml` selects where the blobs go. `cached` keeps a local cache over a
remote store, such as a bucket:

```toml
[plugins.cas]
provider = "cached"
evict_after_days = 30
local_max_gb = 200
remote = { provider = "s3", url = "s3://my-bucket/piloop" }
```

The [configuration reference](/reference/configuration#plugins) lists each provider and its keys. `gcs` needs the
`gcs` extra: `uv tool install --reinstall 'piloop[gcs]'`. A package can add a provider: see
[CAS providers](/architecture/extension-points#cas-providers).

- **Mirror.** Every blob is uploaded as it is stored. For S3, boto3 finds the credentials (environment, profile or
  instance role).
- **Eviction.** Every hour, before the next archiving, the daemon drops the local copies of blobs that the remote
  holds: those older than `evict_after_days`, then the oldest ones until the local store fits `local_max_gb`.
  `piloop store evict` does the same on demand. It first uploads any blob that was stored before you set the remote.
- **One remote per store.** The first upload writes the remote's URL to `$PILOOP_HOME/store/remote.url`. A store
  whose blobs went to one remote refuses to open over another remote, or as `disk`: the blobs it marked as uploaded
  are only in the first one. To move to a new remote, copy the objects there, then write its URL into that file.

`piloop store verify` checks that every blob of every archive is still there. It hashes the local copies again and
asks the remote for the evicted ones.

## A store for other machines

`piloop cas serve` serves this home's store over HTTP to [workers on other machines](/guides/remote-workers), which
reach it with the `http` provider.

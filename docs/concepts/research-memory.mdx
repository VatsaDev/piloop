One database holds every campaign that piloop ran. So a new campaign does not pay again for what an old one learned.
Agents read this memory with SQL. The procedures in every brief (`piloop schema`) have the queries.

## Lessons

A **lesson** is the conclusion about one mechanism family (`ideas.family`) of a campaign:

```sql
INSERT INTO lessons (campaign_id, family, status, effect, metric, body, created_by)
VALUES (1, 'stronger generic compressor', 'promising', -976922, 'bytes',
        'LZMA1 at preset 9 extreme (idea#1, candidate#2) beat zlib by 976922 bytes; the time guardrail held.', 'orchestrator');
```

- `status` is `dead`, `promising` or `untested`.
- `effect` is the best effect measured, in the units of `metric`, with its sign. It is NULL when nothing was measured.
- `body` says why, with idea and candidate ids.

A lesson is never changed: a newer one for the same family replaces it. When a limit of the stop rule ends a campaign, the
closing watchdog writes a lesson for each family that the campaign tried.

The briefs of implementers and research sweeps open with the current lessons on the same repository, also from
campaigns in other clones of it. Each family gets one line, ranked by metric, status and size of the effect.
`[memory] wake_budget` limits these lines, and 0 turns them off.

## Documents

Name the reports and notes that agents should be able to search:

```toml
[memory]
documents = ["docs/evidence/**/*.md"]
```

`piloop init` and the stop of a campaign copy them into the `documents` table. An edited file is a new version.

<Warning>
  Every agent of every campaign can read the documents. Never name one that comes from validation or test data.
</Warning>

## The orchestrator's journal

An orchestrator session can lose its context. The **journal** lets the next session continue the work:

```bash
piloop journal "lesson on lzma recorded; idea#2 (context mixer) is next, p1"
```

A line has at most 280 bytes, and no agent can change it later. `piloop wake` prints what a new session needs first,
in a fixed budget: the latest journal lines, the open inbox, the head of each active campaign and the current lessons.

```text
## Journal, oldest to newest (1 lines in all)
- 2026-10-22 05:02 orchestrator: lesson on lzma recorded; idea#2 (context mixer) is next, p1

## Inbox (0 open)
- none

## Active campaigns (1)
- enwik8 · head bytes 2711853 (candidate#2, -976922 vs baseline) · 2 kept / 2 candidates · 356k tok

## Current lessons on their repos (1)
- [enwik8] stronger generic compressor | promising | -976922 bytes (lesson#1)
```

The `piloop-operate` skill runs `piloop wake` first, and writes to the journal as it goes.

## Sessions

The candidates show what the code was. The **sessions** show what the agents did: their prompts, tool calls and
reasoning. Each harness keeps its sessions in its own store, such as `~/.claude/projects/`. piloop records the id of
each agent's session, and the file that it read the agent's tokens from.

To find the session that made candidate 2:

```bash
piloop sql "SELECT s.session_id, s.usage->>'$.source' FROM agent_sessions s JOIN candidates c ON c.run_id = s.run_id WHERE c.id = 2"
```

The file is the session's transcript, one JSON record for each prompt, tool call and answer. The harness keeps it for as
long as its own settings say.

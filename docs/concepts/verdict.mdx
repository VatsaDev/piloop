## Candidates

A **candidate** is one state of the code, identified by its git tree. Each commit that a worker makes is a candidate.
The baseline that `piloop init` measures is the first one.

Because a candidate is a tree, a commit that goes back to a known state is that known candidate, and piloop does not
measure it again. It keeps its verdict, unless another run reaches it: then the daemon's verdict, if it is not a keep,
is judged again on that run's bar. A keep stays. A run's commits are its first-parent history, so a line that a worker
merges in is not the run's, and a merge's parent is the commit it merged onto. A candidate can have several
measurements. Its score is their mean under the current
[evaluator](/concepts/campaigns#evaluators).

## The head and the bar

The **head** is the latest kept candidate on the trunk. New runs start from it, unless an idea pins another starting
point.

Each run is judged against its **bar**. The bar starts at the base of the run. When the base is not a keep or a
reference (a pinned `interesting` candidate, for example), the bar starts at the nearest kept ancestor of the base. The
bar moves to each keep that the run makes. A run that starts from the head has the head as its bar. Each keep on the
trunk beats the head before it, so the trunk is a chain of improvements. A branch keep that a trunk run merges is not
its bar: the merge must still beat the head.

## The verdict

The daemon gives each measured candidate one verdict:

| Verdict | Meaning |
|---|---|
| `keep` | The primary metric beat the bar with confidence, and every guardrail held. On the trunk, the candidate becomes the new head. |
| `interesting` | The primary metric improved, but without enough confidence, or a guardrail got worse by more than its margin. |
| `discard` | The primary metric did not improve, or a guardrail went past its floor. |
| `crash` | The candidate has no successful measurement: the evaluate command failed or timed out, wrote a bad per-unit results file, or did not print every metric in `piloop.toml`. |
| `reference` | A starting point imported with `piloop candidate import`. It is never judged. |
| `unmeasured` | A commit marked `Piloop-Eval: skip`. It is never measured or judged, and says nothing about its idea. |
| `recovered` | What a worker left uncommitted when it stopped, committed by the daemon (`Piloop-Recovered: run#<id>`). The worker never declared it ready, so it is never measured, judged or kept. If its run did not succeed, the idea goes back to the queue with it as the base, so a new worker finishes it, up to `[roles.worker] recovery_requeues` times per idea (2). |

The rule, in order:

1. No value for the primary metric: `crash`.
2. A guardrail past its `floor`: `discard`.
3. The bar has no score under the current evaluator: `keep`.
4. The primary metric is not better than the bar: `discard`.
5. The primary metric is better, but its worst case at the `confidence` level is not above zero: `interesting`.
6. A guardrail's worst case is worse than the bar by more than its `margin`: `interesting`.
7. Otherwise: `keep`.

Each verdict has a reason. This one is from the enwik8 example campaign:

```text
against candidate#33: bytes 2361893 vs 2365922 (-4029; aggregate: no per-unit results); guardrails: seconds 24.48 vs 23.28 (+1.2; aggregate: no per-unit results) within its margin 10
```

The reason names every guardrail past its floor or beyond its margin, whatever rule decided the verdict. So the
reason of a `discard` on the primary metric still shows a large regression of a guardrail:

```text
against candidate#33: bytes 2365922 vs 2365922 (+0; aggregate: no per-unit results); guardrails past their margin: seconds 41.3 vs 23.28 (+18.02; aggregate: no per-unit results) beyond its margin 10
```

A candidate whose primary and guardrail values equal those of its parent has `no-op` in its reason. The change did
not reach what the evaluate command measures.

## Metric roles

- **primary**: the metric to improve. It must beat the bar with confidence for a `keep`.
- **guardrail**: a metric that may get a little worse. `margin` is the largest regression from the bar that is
  allowed, in the metric's own units. `floor` is an optional hard limit on the value itself: at least the floor for
  `higher`, at most the floor for `lower`.
- **watch**: recorded, and never part of the verdict.

A margin applies to each step. Many keeps that each give up a margin can add up to a large regression. A floor stops
that. Only an edit of `piloop.toml` moves a floor.

<Note>
  Put every margin and floor in `piloop.toml`. A limit that is only in `brief.md` is a request to the agents. A limit
  in `piloop.toml` is enforced by the daemon.
</Note>

## Confidence

When the evaluate command writes [per-unit results](/concepts/campaigns#per-unit-results), the verdict uses a paired
bootstrap over the units:

1. Take the units that the candidate and the bar both report, and the difference of each.
2. Resample the units with replacement 4000 times, and sum the differences each time.
3. The worst case is the `1 - confidence` quantile of these sums. With the default `confidence = 0.95`, it is the 5th
   percentile.

So a gain that comes from three units has the spread of three units, not of the whole test set. The random generator
has a fixed seed, so the same numbers always give the same verdict.

Without per-unit results, or when the two sides report different units, the verdict compares the aggregate values.
Any gain then counts, and the reason says `aggregate`. This is right for a deterministic metric, such as a compressed
size. For a noisy metric, write per-unit results.

## Replace the rule

The rule on this page is the built-in verdict rule, `bootstrap`. A plugin can add another verdict rule, and you
select it in `piloop.toml`. For example, the example plugin `examples/plugins/min-gain` adds the rule `min_gain`. It
keeps a candidate only when the candidate beats its bar by at least `min_gain`:

```text
[plugins.verdict_rule]
provider = "min_gain"
min_gain = 100
```

piloop gives the rule the metrics that decide, `confidence`, the measurements of the candidate and of its bar, and
the rule's parameters. The rule returns `keep`, `interesting`, `discard` or `crash`, and a reason. The rest of this
page stays the same with any rule: the bar, the head, the merge when the head moves, and the `no-op` note.
[Verdict rules](/architecture/extension-points#verdict-rules) has the details.

## When the head moves during a run

Two runs can start from the same head. When the first one keeps, the head moves. If the second one then beats its own
bar, it is `interesting`, with a reason that starts with `keeps against its own bar, but the head moved on`.

The daemon then merges the second candidate onto the new head, as a commit with two parents. The merge is a new
candidate of the same run, and the daemon measures and judges it against the new head. If the merge has conflicts,
the daemon files a seed `Compose candidate#N onto the head` instead.

## Measure a candidate again

A fault of the host, such as a full disk, can crash a measurement of good code. The same tree committed again is the
same candidate, so the daemon does not measure it again by itself. Ask for it:

```bash
piloop candidate remeasure 42
```

The daemon measures the candidate again with the current evaluator, after the head and the bars that runs need. A
`crash` that the daemon judged is judged again with the new measurement, as its run would have judged it. Any other
verdict stays, and the new measurement is one more repeat in the mean. A `pending`, `unmeasured` or `recovered`
candidate is never measured this way. A stopped campaign is measured too, but only what someone asked for, so you can
measure a result again when you review a campaign. A campaign paused with `--evals`, or held by its stop rule, is
measured once the hold ends. The command says when.

## The evaluation queue

The daemon runs at most `max_evaluations` evaluate commands at the same time, across all campaigns (2 by default, in
`config.toml` or `PILOOP_MAX_EVALUATIONS`). The others wait in the evaluation queue. A free slot goes to the campaign
with the fewest running evaluations, and in that campaign to its head first (the runs that start from the head wait
for its score), then to the oldest request. So a busy campaign never holds back another one. The order in which a run
measures its own commits does not change.

A tree is evaluated once: a second request for a candidate that waits or runs waits for that evaluation.

```bash
piloop eval queue
piloop eval cancel 42
```

`piloop eval cancel` cancels the evaluation of one candidate: a waiting evaluation never starts, and a running one is
stopped. The candidate gets a crashed measurement that names who cancelled it at once, so a candidate of a run is
judged a `crash`, and a daemon restart does not evaluate it again. Like any crash, it is measured again only when
someone asks (`piloop candidate remeasure`).

## Override a verdict

Any agent or human can change a verdict and say why:

```bash
piloop candidate verdict 42 interesting --reason "lucky seed"
```

The daemon never overwrites a verdict that it did not set. The `candidate.verdict` event records the change with the
reason. Only a judgement (`keep`, `interesting`, `discard`, `crash`) is overridden, and a keep must build on the head
unless its run is a branch run: the head is the newest trunk keep, so a keep from an older bar would drop what the head
kept since.

## Add a measurement by hand

When you ran the evaluation yourself, for example after the daemon's evaluation timed out, record it:

```bash
piloop measurement add 42 --report report.json
```

`report.json` is `{"metrics": {"accuracy": 0.853}, "seconds": 600}`, with the metrics of `piloop.toml`. The
measurement counts under the current evaluator. When the verdict is the daemon's `crash`, `discard` or `interesting`,
the daemon judges the candidate again with all its measurements, as its run would have judged it. A keep stays: runs
started from it as their bar, and they must now beat its new mean. A pending candidate is refused until the daemon
has judged it.

## Notes

A result that regressed can still be a good starting point. A **note** keeps it in view:

```bash
piloop candidate note 42 "faster tokenizer, but loses accuracy on long inputs" --follow-up "fix the long-input case"
```

The candidate becomes `interesting`, with a reason that starts with `note:`, followed by its earlier reason. Each
`--follow-up` files a seed pinned to the candidate. A note is not a keep, and it does not move a bar. A worker notes its
own commit with a `Piloop-Note: <why>` trailer in the commit message.
